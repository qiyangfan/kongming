# 设计:文档多查询分解召回

## 上下文

- 文档问答链路:`understand` 改写问句 → `route_intent` 三态判定 → `retrieve`
  单次双路召回(RRF → 父块 top-5)→ `doc_answer`/`fused_answer`。
- 30 题真实公开文档诊断:失配题的 gold 父块多数不在任一路 top-8、也不在
  融合前 10;父块 top-5→8 只修回 2 道整题,跨文档全跳仍 0/6。
- 实验室判别(模型拆分 → 逐子查询现有召回 → 父块并集):同文档多跳全跳
  0.667→1.000;跨文档 0/6→1/6;朴素拆分单跳 1.000→0.833(原问信号丢失)。

## 决策

1. **复用既有意图调用,不新增 LLM 轮次**:`route_intent` 已在检索前调用,
   在同一个 JSON 帧增加 `subqueries` 字段;最大输出 token 200→400。
   多跳判定与子查询由同一次调用产出,失败仍走既有低置信/失败回退。
2. **原问句永远保留**:retrieve 先做原问句检索,子查询只做增量合并;合并
   顺序原问句优先。这样单跳路径的召回与提示内容与引入前逐字一致,朴素
   拆分伤单跳的问题不再成立。
3. **只对 knowledge/fused 生效**:data 意图丢弃 subqueries(解析层保证);
   schema、指标、历史 SQL 只取原问句结果,SQL 链路零变化。
4. **合并按引用键去重、总量上限 8**:citation_key 由父块主键派生,天然
   稳定;上限 8 = 原 top-5 + 最多 3 条增量,控制提示体积。doc_answer 与
   fused_answer 的文档段注入上限同步改为 8;单查询仍只返回 5 条。
5. **召回上限仍代码固化,不做运行时配置**:`_CHILD_TOP_K`/`_PARENT_TOP_K`
   与质量口径、索引文本、嵌入模型绑定;运行时可变会让线上行为与评测基线
   异源。调优走评测矩阵(probe 的 `parent_top_k` 只作诊断,不改变主检索)。
   同帧的子查询条数上限(3)与提示注入上限(8)一并固化。
6. **并行补检、失败降级**:子查询召回并发执行;单条失败/空结果忽略,原
   问句命中保留;不新增失败终态、不改路由判定。

## 验收口径(运行前登记)

- 单跳不回归:实验室 30 题单跳组 full-hop 保持 1.000;15 文档 28 题与
  实验室 74 题按既有红线(5pp)复核。
- 同文档多跳:full-hop 由 0.667 提升,预登记 ≥5/6。
- 跨文档多跳:仅报告,不设通过线;已知受子查询自身候选精度限制。
- 链路等价:无子查询时 `rag_retrieve` 调用次数、doc_hints 内容、schema/
  metric/history 段与引入前一致;引用键、接口与数据库不变。
- 单元:解析门控(data 丢弃、knowledge/fused 保留、上限 3、去重)、合并
  (引用键去重、原问优先、上限 8)、失败降级(子查询 None/异常)与单查询
  零额外调用。

## 风险与回滚

- 风险:小模型在意图帧内拆分的质量不足;提示词已限定「保留专有名词、不得
  改写为陈述句」,失败时原问句路径兜底。必要时经既有模型路由把
  INTENT_ROUTE 调到更强模型,不新增调用轮次。
- 风险:多跳问题上下文 5→8 条带来提示变长;上限 8 与每块 1500 字截断约束
  体积,跨文档收益不承诺。
- 回滚:回退本变更的提示字段、解析、retrieve 合并与注入上限;无数据迁移,
  索引不需重建。
