# 081-external-knowledge-tool 设计要点

## D1 为什么工具收口控制面,而不是 agent 面直调 siku

三个理由,按权重排序:

1. **信任边界(ADR-002)的既有形态**。孔明的双进程边界立的是「agent 不持凭证、外部调用收口控制面」。siku 端点恰好无鉴权(localhost), agent 直调在本场景不泄露新凭证——但「这个端点无鉴权所以可以绕过边界」是把安全判断建立在外系统的当前属性上:siku 明天若给 `/api/*` 加 key(其代码里已有 `api_key_env` 错误映射的痕迹),直调方案就要给 agent 注入凭证,边界当场降级。收口控制面使边界判断与外系统演进解耦。
2. **审计单点**。工具调用审计(成败/耗时/越权)已有落库范式;直调等于给检索开一条无审计通道,「每次执行留痕」的产品承诺出现豁免区。
3. **配置校验单点**。白名单与单租户闸放在控制面启动装配处,与 021 注册表纪律同构;放到 agent 面就是把两套白名单纪律并行维护。

## D2 为什么接 `/api/search` 而不是 `/api/ask`

`/api/ask` 是 siku 的完整问答(检索 + siku 自己的 BYOK LLM)。接它意味着:孔明的每个用户问题可能触发两套 LLM(siku 一套、孔明一套),双倍成本;答案绕过孔明的护栏/审计/数据权限;模型与 prompt 不可见不可调。`/api/search` 是纯检索,结果作为**证据**进入孔明 agent 自己的 ReAct 循环——答案仍由孔明的模型产出、仍过孔明的护栏。这正是工具化(tool)与链路替换(pipeline)的区别。

## D3 白名单为什么包含 `host.docker.internal`

白名单名义是「仅本机」。但孔明的既定部署形态是 compose 容器(`infra/api.Dockerfile`),容器内的 `127.0.0.1` 不是宿主机的 `127.0.0.1`;macOS Docker Desktop 下容器到宿主机的标准形式是 `host.docker.internal`。不收它,compose 部署形态下这个工具永久不可用(只能退回 `network_mode: host` 这类破坏性部署变更)。收它的风险敞口与 127.0.0.1 等价——解析目标仍是本机。其余主机一律拒配。

## D4 单租户闸为什么是启动检测而不是运行时开关

个人 vault 没有租户维度。若允许多租户部署注册,所有租户的 LLM 都能检索同一份个人文档——这是数据越界,且没有任何 UI 能「修复」它(要么回不去,要么每租户各挂各的 vault,那是另一个产品)。启动检测 + 告警是最小实现:多租户是显式动作(建第二个租户),不存在「不知不觉越界」的路径。探测放启动而非每请求:租户数是低频变更,且每请求查库是把闸门做成了热路径。

## D5 为什么双库检索不融合

孔明 RAG 三路召回(schema 向量 / 全文 / SQL few-shot)与 siku 检索各有一个「口径世界观」:前者是数据库语义层,后者是个人文档。把两路命中丢进同一个 rerank 排序,用户无法分辨「这条口径来自业务库还是来自三年前的一份 notes」——口径混淆在问数场景里直接产出错误数字。v1 让两路并列:agent 自主选择用哪路,答案标注来源锚点。未来若融合,前提是统一口径归因(每条命中带库级 provenance 且可过滤),那是独立 change。

## D6 重试分层:连接层一次,响应层零次

复用 072 已落地的只读分层语义(只读回调连接层未送达可重试一次;响应类错误不重试)。检索是幂等读,单 localhost 点对点,失败几乎只有两种成因:siku 没起(连接层,重试一次可吸收启动竞态)或端点返回错误(响应层,重试无意义且放大噪声)。不再引入第二套重试原语。
