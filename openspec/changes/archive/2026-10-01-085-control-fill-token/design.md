# 085 设计：控件填充语义的归位方式

## D1 拆出新 token，而不是回退 `--input`

回退 `--input` 到 hairline 值能一次性消除填充回归，但那等于放弃 084 的 ≥3:1——
未勾选复选框重新隐身，是更严重的那个缺陷。两个语义混在一个 token 上时，
修任一侧必然连带另一侧，唯一稳的解法是**先分离语义再分别定值**。
本批之后：`--input` 只对描边负责，`--input-fill` 只对底/轨道负责，两侧可独立演进。

## D2 填充不复用 `--border`，哪怕数值相同

最省事的写法是让填充继续读 `--border`（它的值本来就等于拆分前的 `--input`）。
不取：那会把 `--border` 变成「分隔线 + 卡片描边 + 控件填充」三重语义，
下一次有人为了控件底色调它，就会把全站分隔线一起带走——正是 084 立项时描述的那类事故。
数值相同是**当下的巧合性一致**（都取自中性 hairline 族），语义必须各自独立命名。

## D3 取值口径 = 084 拆分前的原值，逐字节零漂移

填充侧本批无任何需求，因此判据只有一个：**渲染结果与 084 之前完全一致**。
kongming/jinguan 亮 `#dfe3de` 暗 `#2a363a`、muniu 亮 `#e2e2de` 暗 `#2b302a`，
即各仓 084 前 `--input` 的字面值。「先搬回原值」而非「重新挑一个好看的填充色」，
是为了让本批 diff 可以被逐条判定为纯修复，不混入未授权的外观变更。

## D4 命名 `--input-fill`，不用 `--control-surface`

shadcn 标准件的类名是 `bg-input`，`--input-fill` 与之同族、可读为「input 的填充面」，
`ui/*.tsx` 的 diff 是同一槽位加后缀，未来跟上游标准件对照不至于失配。
再造一套 `--control-*` 词汇会让三仓 token 表出现第二个命名体系，违背宪法 Article 1 词汇统一。

## D5 接线判据取构建产物，不取肉眼

`bg-input-fill` 属于「拼错不报错」的一类：token 若未在 `@theme` 注册或类名写错，
Tailwind 直接不生成该规则，样式静默丢失，开关轨道会变成透明——
`stylelint`/`eslint`/`tsc` 都查不出来。因此判据定为**在三仓 `vite build` 产物 CSS 中确认**
`.bg-input-fill*` 规则存在且解析到 `var(--input-fill)` / `var(--color-input-fill)`，
再由真浏览器读计算色复核（亮/暗两态）。肉眼截图只作状态观感的旁证，不作接线证明。
