# 拆分转义并显式区分 SQL 模糊模式

## Why

`kongming/like.py` 将 LIKE 字面量转义与包含匹配模式拼装放在同一函数中：前者负责处理 `\\`、`%`、`_`，后者负责在转义结果两侧添加 `%`。这两个职责分别属于转义工具与 SQL 工具；混在 `like.py` 让转义规则和具体搜索策略无法独立理解与复用。

四个仓储域目前都使用大小写不敏感包含搜索，但包含、前缀和后缀匹配是不同的查询语义，也对应不同的索引机会。SQL 工具需要显式表达模式方向，仓储才能按具体搜索需求选择；模式方向本身不代表索引一定生效，索引策略还须与 `LIKE`/`ILIKE` 语义和排序规则匹配。

## What Changes

- 将 LIKE 字面量转义提取到 `kongming/escape_util.py`，由 `escape_like_literal` 只处理 LIKE 元字符。
- 将 SQL LIKE 模式拼装提取到 `kongming/sql_util.py`，分别提供前缀(`keyword%`)、后缀(`%keyword`)和包含(`%keyword%`)匹配函数；每个函数调用转义工具后再添加通配符。
- 将 chat、datasource、store、system 仓储的内部调用迁移到对应工具；现有调用继续选择包含匹配，并移除旧的 `kongming/like.py`。
- 在设计与验收中区分匹配模式和索引策略：前缀模式须验证 B-tree 适用条件；包含/后缀模式按实际查询评估 trigram 等索引，并以查询计划证明效果。
- 保持现有模式字符串、`ILIKE`、`ESCAPE '\\'`、参数绑定及对外搜索语义不变。

## Capabilities

本变更只调整内部代码职责，不改变行为契约；无需新增或修改 capability spec，`.openspec.yaml` 标记 `skip_specs: true`。

## Impact

- **代码**：`apps/api/kongming/like.py`、新增 `escape_util.py` 与 `sql_util.py`、四个仓储模块及相应单元/集成测试。
- **兼容性**：不改变 HTTP/API 或搜索结果；只迁移仓储内部的 Python 导入。
- **索引**：针对具体查询验证索引策略；当前不预建索引，只有基准与执行计划证明具体字段能获益时才增加迁移，并遵循 ADR-004。
- **验证**：检查三类模式的纯函数结果；对实际优化的查询使用代表性数据检查执行计划与缓冲区访问，并运行 API 相关测试和质量门禁。

## Non-goals

- 不切换现有搜索入口的匹配语义；会话、数据源、用户和商店搜索继续使用包含匹配。
- 不调整 `ILIKE` 的大小写语义，不改变搜索结果或参数绑定方式。
- 不声称前缀模式必然命中 B-tree，也不为没有代表性数据和执行计划证据的列预建索引。
- 不提供含义不明确、跨语法复用的通用 `escape()`；不同文本语法需要各自明确的转义规则。
- 不新增依赖、OpenAPI 变更或其他 SQL 工具框架；不在缺少查询计划证据时预建索引迁移。

若后续执行计划验证决定新增索引迁移，按 `docs/adr/004-schema-baseline.md` 的 schema 纪律执行；该迁移不改变搜索结果契约。
