# 082-knowledge-tool-multitenant-warning 设计要点

## D1 为什么是「告警」而不是「拒注册」,也不是「删闸了事」

失败形态排序:**静默失效**(拒注册:功能消失,只有一个没人看的日志行)> **显性故障** >
**带告警的正常工作**。081 的单租户闸取的是最差形态;本变更把它移到最好形态:
功能照常,风险用启动告警 + spec 条款双通道显性化。删闸了事(连告警都不要)会丢掉
「未来操作者知道这工具在租户间是共享的」这一事实——告警是这个事实的最低成本载体,
保留租户计数查询正是为它(约 3 行)。

## D2 为什么不顺手做租户级隔离(028 模式)

028 mcp-interop 已有完整范式:租户级 server 配置、快照注册、`mcp__<serverKey>__<tool>`
命名、动态解析。把知识源迁进该模式 = 新增租户级配置 CRUD + 加密落库 + 快照同步 +
注入过滤,对一个 owner 明示不会出现的第二人类租户,是纯负债。触发条件写进 spec
Non-goals:出现真实第二个租户时立独立 change 迁入,不在此铺垫半套。

## D3 为什么 localhost 白名单不同类、不动

两道否决条件(未配置/主机非法)判的是**端点存在性与形态**——错误配置下工具本就毫无
意义,拒注册 + 告警是把「配置错误」前移到启动时,零假阳性(合法使用者主机必然在
127.0.0.1/localhost/host.docker.internal 集内,owner 现网即 127.0.0.1)。单租户闸判的
是**环境状态**——同一个合法配置在不同租户数的库上行为分叉,这才是假阳性来源。
两类闸不同构,只降后者。

## D4 对 081 的废止关系

081 design D4「单租户闸为什么是启动检测而不是运行时开关」的论证前提(多租户是
真实威胁)被 owner 的环境事实否证;其「半正确实现比诚实限制更危险」的结论反过来
支持本变更——让工具在所有环境可用 + 把共享面诚实地写进 spec 与告警,比用一个
闸假装解决问题更诚实。081 归档件的历史记录不改(它是当时的最优解),本 delta
归档后主 specs 以本变更为准。
