# 055-usage-cost-reconciliation 设计:方案谱系与取舍

## 问题定性

双轨本身不是缺陷:产品轨(向租户收费的牌价)与成本轨(muniu credit 计量的真实支出)服务不同目的,允许加成与折扣。缺陷是**两轨间零对账**——成本侧的任何异常(上游改价未同步、计量漂移、模型路由打错价档、币种换算错误)对 kongming 完全不可见,账单背离成本只能靠人肉翻两套系统发现。

## 方案谱系

### 方案 A:muniu 直推 kongming(muniu HANDOFF 6b 原裁决)

kongming 实现 ingest 接收端点,muniu `metering.sink=ingest` 推送 usage 行,下线自有模型计价。

**否决理由(本 change 对 6b 的谱系修订)**:

1. **管道已被占用**:muniu 计量汇是单 sink 插拔(ADR-0007),ingest 通道已归属控制面锦官(jinguan `IngestController` 落地且跨仓联调,含欠费停服闭环)。为 kongming 复用该通道需把 muniu 改为多 sink 广播——为对账需求改动数据面投递拓扑,代价与收益不成比例。
2. **归账真相分叉**:jinguan 按 `api_key_bindings` 把 usage 行归账到用户并驱动钱包扣费;kongming 若并行接收同一批行并按自有租户记账,同一笔用量存在两套独立归账,后续对账反而要对「两套归账」再对账,问题递归。
3. **「下线自有计价」在身份统一前不可行**:kongming 开发者门户的租户体系与锦官用户体系尚未统一,自有牌价计费(套餐/配额/账单)是租户产品能力,下线它等于下线开发者门户计费本身——超出了「成本可见」的原始诉求。

### 方案 B:kongming 定期从锦官控制面拉取用量汇总

以锦官(归账权威)为取数源。**暂缓理由**:锦官侧「平台→kongming 租户」的归属维度尚不存在(锦官归账到锦官用户,不感知 kongming 租户),当前取回的汇总粒度与 kongming 账单周期对齐所需维度不匹配;待锦官统一身份演进落地后,B 是自然归宿(登记为长期演进,不在本 change)。

### 方案 C(采纳):只读旁路,直取 muniu 管理面汇总

kongming 管理面新增只读对账端点,直接调 muniu `GET /admin/v1/usage`(gateway-parity 已落地的既有契约,muniu 侧零开发),按时间窗取 key 维度 credit 汇总,与本侧 `sys_llm_usage`/`sys_invoice` 汇总并列输出,偏差率超阈值记审计告警。

- **零跨仓代码改动、零新契约**:只用 muniu 既有管理 API;两仓契约面不变。
- **fail-open 但显式标注**:对账是纯读旁路,拉取失败不影响计费主链路,报告必须显式标注「成本侧不可用」而非静默空值——可观测性缺口不允许以「看起来正常」的方式降级。
- **量级比对而非硬换算**:厘(产品牌价)与 credit(成本)不强行折算,比较总量级与偏差率;阈值告警给出「需要人看」的信号,不试图自动裁决哪侧正确。

## 残余风险与登记

- muniu 管理 token 在 kongming 环境中的保管(环境变量注入、不入库不入日志)是新增凭证面,收口于 2.2 任务;泄漏影响面 = muniu 管理面只读+管理操作,与运维已有的 muniu 管理 token 同级。
- 对账粒度是「同期汇总」,单笔用量级差异不可见——本 change 的目标是成本失控可见,不是逐笔审计;逐笔归账统一依赖锦官身份统一(长期演进)。
- muniu 灰度期内(ADR-007)对账基线本身在波动,偏差阈值告警在灰度收口前只观测不设硬门。
