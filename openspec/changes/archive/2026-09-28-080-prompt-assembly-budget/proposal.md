# 080-prompt-assembly-budget 提案:生成提示词装配预算(超限不再硬失败)

## Why

全仓**没有任何上下文预算概念**,一条可证的上界都不存在:

- `apps/agent/kongming_agent/settings.py:25-37` 的 `ModelEntry` 只有
  `name/base_url/api_key/model/capabilities/max_image_mb/protocol`(另有
  两个零读点的 `price_*` 残留字段,由 075-model-registry-pricing-removal
  清除)——**没有上下文窗口字段**;全仓无 token 计数(grep 零命中)。
- 现有约束全都是"**选多少**"而不是"**有多大**":`MAX_HISTORY=5`、
  文档 `top-5` + 每段 1500 字符、`meta_schema_max_tables=50`(限表数)、`RECALL_TOP_K=5`。
- 真正无界的段有好几个:`schema_hint` 里每张表带**全部列说明**(知识上传面对长度无上限)、
  `relations_hint`、`metric_hints`、056 的 `skill_terms`/`skill_examples`(术语与黄金示例
  可任意增长)、`history_sql`(成功 SQL 原文)、`memory_hint`(记忆召回注入)。
  一个 50 表租户的表结构段就足以独自顶穿窗口。

### 后果不是降级,是**确定性锁死**

超限时 provider 直接 400。本仓的映射链是:`LlmError` → 终态
`success=false` + 文案「LLM 服务暂不可用,请稍后重试」→ `chat_message.status='FAILED'`。

于是三件事同时发生:

1. **用户重试无用**——输入没变,提示词没变,每次都是 400。该租户在该问法上被永久锁死;
2. **归因是假的**——文案说"服务暂不可用",真实原因是"我们自己的装配超了预算"。
   运维按服务故障去查 provider 侧,查不到任何东西;
3. **管理面看不出来**——`sys_llm_usage` 在该次调用记 `status=ERROR, tokens=0`
   (`llm.py:_report` 覆盖失败路径,这点是对的),但没有任何字段说明"输入过大",
   只有 `/admin/usage` 时间线里一条 ERROR。

这是最坏的一类故障形态:确定性失败 + 误导归因 + 无自愈路径。而 063 的相关表预筛
只是把概率压低,**不与本变更互为替代**——预筛之后仍然没有任何上界。

参考问答线在这一层的做法有两点值得整体搬过来,其中第二点是本仓完全没意识到的:
① 预算按**每模型窗口**算,窗口取自模型配置、缺省回退;
② 截断方向有硬纪律——**历史段只从最旧端丢弃,绝不中间删或重排**,
理由不是可读性而是**让提示词前缀保持字节稳定,从而吃到 provider 侧 prompt/KV 缓存**;
按"哪段不重要就砍哪段"的跨段裁剪曾被该仓实现过又**删除**,因为尾切历史与前缀稳定性
直接冲突。这是一条真实成本杠杆,不是安全带的副产品。

## What Changes

1. **注册表条目可携带上下文窗口**:`ModelEntry` 增可选 `context_window`,
   未声明时 SHALL 回退全局可配缺省值;预算 = 窗口 − 预留输出 − 安全边际(均可配)。
2. **装配后、送模型前有上界校验**:超限 SHALL 按分段优先级收敛,
   SHALL NOT 让整轮以 400/FAILED 收场。
3. **两条截断纪律(都有成本或正确性理由,不是随手为之)**:
   - 历史段 SHALL 只从**最旧端**丢弃,SHALL NOT 中间删或重排——保持提示词前缀字节稳定,
     这是 provider prompt/KV 缓存可命中的前提;
   - 证据段(表结构 / 术语 / 示例 / few-shot)SHALL 按预筛名次从尾部丢弃,
     且**首位豁免预算**(首位是最高相关命中,砍它等于自废召回)。
4. **不可切段**:系统提示的纪律段与本轮问句 SHALL NOT 被截——把正确性与安全性
   换成成本是本末倒置。
5. **估算保守、零新依赖**:按字符长度分档估算即可,MUST NOT 为估算引入第三方
   分词器(`docs/tech-stack.md` 锁栈;且精确计数对此用途是过度工程)。
   预算触发点 SHALL 可与 `sys_llm_usage` 已采集的**实际 prompt tokens** 对照校准。
6. **触发可见**:被裁段落、裁切量、估算与实际偏差 SHALL 进 trace,
   与 063 的可解释性口径一致——**SHALL NOT 静默降质**。
7. **零回归**:正常轮次 SHALL NOT 因本变更产生任何字节变化;预算只在超限路径生效。

## Non-goals

- **不引入精确 tokenizer**(见第 5 点);不做"按模型词表逐 token 计费式截断"。
- **不做历史摘要式压缩**(另立能力:涉质量取舍且多一次模型调用,与"省预算"动机相悖)。
- **不做按请求动态调 top-N**;063 已把动态自适应列为非目标,此处同样不做。
- **不做超限自动降档到更小模型**——那是反向操作(为塞进去而换弱模型,质量代价更高)。
- **不做输出侧预算**:`max_tokens` 与行上限已存在,本变更只管入参装配。
- **不做列级裁剪**(与 063 的非目标一致);**不改 provider 参数与出站协议**。
- **不与管理台阈值 UI 联动**:先用环境变量,数据证明需要可配再立变更。

## Capabilities

### Modified Capabilities

- multi-model-routing:注册表条目 SHALL 可声明上下文窗口(可选,缺省回退),
  作为装配预算的输入。

### Added Capabilities

- nl2sql-agent:新增「生成提示词装配预算」Requirement——送模型前校验上界、
  超限按段收敛且方向有纪律(历史最旧端 / 证据尾端首位豁免)、触发可观测、正常轮次零回归。

## Impact

- **落点**:仅 `apps/agent`——`settings.py`(`ModelEntry` 与两项预算配置)、
  `graph/nodes.py:generate` 的 user 提示装配段(`nodes.py:213-246` 的八段拼接)、
  一个新增纯函数(估算 + 按段收敛,零 IO、零框架,受 import-linter 覆盖)。
- **无 OpenAPI 信封变更**(ADR-005):注册表经环境变量声明,`context_window`
  不出现在响应里;若为 trace 新增字段则 `make contracts` 并提交产物。
- **无 schema 变更**(ADR-004)。
- **信任边界(ADR-002)**:全在 agent 进程内的字符串处理,无新增回调、无新增凭证。
- **与 063 的关系**:063 决定"注入哪些表",本变更决定"拼出来不能超过多大"。
  两者独立落地、独立回退;**063 未落地时本变更收益更大**(现在就能挡住 50 表硬失败)。
- **运维口径**:落地后 `FAILED` + "服务暂不可用" 的假归因在这一类输入上消失;
  若仍出现 400,说明不可切段本身就超预算,属须上报的配置问题而非静默降质。
