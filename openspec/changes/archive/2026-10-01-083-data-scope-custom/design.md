# 083 设计：CUSTOM 的存储、语义与判定顺序

## D1 关联表，而不是 `sys_role` 上的 JSON 列

`sys_role_dept(role_id, dept_id)`，复合主键 + 两侧 FK + `dept_id` 索引。

- 「某角色圈了哪些部门」与「某部门被哪些角色圈走」都是关系查询，FK 让「删掉还被引用的部门」在库层直接被拒（`DeptInUse` 之外再兜一层）。
- JSON 列三样都给不出：无 FK 完整性（悬空部门 ID 只能靠应用层自觉）、反查要全表扫、集合去重语义要靠代码。ADR-004 的同一纪律：**能用约束表达的不变量，不留给注释与应用层自觉**（该 ADR 用「状态列禁 SMALLINT 魔数」表达这条原则，此处同型）。
- 代价：多一次 JOIN。数据范围解析在问数链路每请求一次，`role_id` 走主键、`dept_id` 走索引，量级可忽略；换来的是库层完整性。

## D2 CUSTOM 宽严排在第二，但语义是「按集合并集」

`PERMISSIVENESS` 里 CUSTOM 仍排 ALL 之后（rbac：多角色取最宽松）。理由不变但含义变了：
集合内容由运营决定，可能比 DEPT 宽（圈了兄弟部门）也可能比 SELF 窄（圈了空集→直接拒绝），
因此它不可能落在 DEPT 与 DEPT_AND_BELOW 之间的某一档——**它的位置只能由集合本身决定**。
本轮保留排序（改排序等于改多角色裁决，属 rbac 契约），并在 models 注释写明这一点。

## D3 CUSTOM 不递归子部门

递归是 DEPT_AND_BELOW 的定义性语义。若 CUSTOM 也展开子树，两档差别只剩「部门来自哪里」，
运营无法解释「为什么我勾了父部门却多出十行」。集合就是字面集合，要下钻就选 DEPT_AND_BELOW。

## D4 fail-closed 判定必须早于降级分支

`applier.py` 原顺序是：解部门集 → 列探测（其中「主表不可定位」会**降级为不过滤**）→ `resolve` 判 UNSUPPORTED。
把 CUSTOM 空集合的拒绝留在 `resolve` 里，就存在一条 **fail-open 路径**：CUSTOM 空集合 + UNION/子查询 FROM
取不到主表 → 先降级不过滤 → 返回全量数据。本轮把 `service.unsupported_reason(ctx)` 提到列探测之前，
`resolve` 处的 `FilterType.UNSUPPORTED` 保留为纵深防线（构造上已不可达，但绝不允许它继续改写）。

空集合也不许改写成恒假条件（`1=0`）：那会让「配置缺失」伪装成「查无数据」，排查成本反而更高——
显式失败是本 spec 的一贯裁决。

## D5 写侧：`None` 与 `[]` 分开，搭配非法即拒

- `data_scope_dept_ids` 缺失（`None`）与显式空数组（`[]`）在 **CUSTOM 档**下都拒：前者防「选了档却没配集合」，后者是明确的空集。
- **非 CUSTOM 档一律清空**（`_resolve_custom_depts` 恒返回空集合 → `rebind_role_depts` 整包替换为空）：
  档位已不消费该集合，留着就是库里挂一份永不生效的授权数据；实测把 CUSTOM 改成 SELF 后
  `sys_role_dept` 行数归零，即使请求体根本不带该字段（走查 2026-10-01 复核，本条修正初稿「None=不动」的说法）。
- 非 CUSTOM 却带非空集合 → 400。静默忽略会制造「界面显示配了、执行侧不生效」的第二套事实。
- 整包替换（先删后插）与既有 `RolePermsIn` 权限绑定同语义，避免两套局部更新规则。
- 部门存在性复用 `UnknownDeptId`（400），不新建同义异常。

## D6 前端：多选控件走「树 + 复选」纯函数拆分

`lib/dept-tree.ts`（扁平部门 → 树 + 键映射）与 `lib/role-scope.ts`（档位与集合字段的可见性/载荷规则）
都是无框架纯函数并带单测；视图只消费它们。理由：档位↔字段的联动是**权限相关逻辑**，
放在组件里只能靠 e2e 覆盖，抽成纯函数后由 vitest 直接钉死。

`warnings` 一类既有区块不复用：部门多选独立成 `components/check-list.tsx`，非 CUSTOM 时整块不渲染，
也不发该字段（避免「隐藏但仍在提交」的陈旧值）。

## D7 两条随行修复为什么在本批做

`make check` 的可复现性被它们挡住：

1. 迁移往返用例 `downgrade("0033")` 后只 `upgrade("0034")`，把库留在 head 之下——本批一加 0035，
   其后每个用例的 `TRUNCATE public.sys_role_dept …` 都撞上 `UndefinedTableError`（实测 518 个错误的唯一成因）。
   修法是回 `head`，用例意图（0034 列契约往返复现）不变。
2. 出账幂等用例的「上月」取自库时钟（UTC），产品用固定 +8 口径 → 每月 1 日 00:00~08:00（北京时间）跨月错位，
   用量写进产品不出账的月份，断言必红。修法是用例改调产品的 `_prev_month()`，时源单一。

两者都是测试侧缺陷，不改任何产品行为；留着的后果是「谁加迁移谁背锅」。
