# Design

## Context

agent 面问答图为 LangGraph 8 节点链路(含 retrieve 双通道检索、doc_answer
旁路);文档检索经 api /internal 回调(ADR-002,agent 零凭证);引用键
形态、编造净化(068)与 sources 投影已在 document-rag/chat 域定契约。
LLM 客户端为 llm.py(openai 兼容,dashscope 直连,multi-model-routing
可配)。约束:数据态问句行为逐字不变(零回归);无新表;契约变更走
make contracts(ADR-005)。

## Goals / Non-Goals

**Goals:**

- 融合态复用 retrieve 阶段已完成的文档检索(不二次检索)
- 路由失败兜底 = 既有词表行为,保证最坏情况退回 093 前形态
- 契约只放宽(sources 融合道可非空),不新增字段

**Non-Goals**(设计级,proposal Non-goals 之外):

- 不做路由判定的Few-shot 示例库(先零样本 + 指令约束,误判率超预期再加)
- 不做融合答的流式差异处理(query-streaming 既有降级口径直接适用)

## Decisions

### D1: 路由节点前置,通道确认保留在 retrieve 后

route_intent 节点放检索前(轻量 LLM 调用,输出三态+置信),既有
「知识态且文档命中才走 doc_answer」的通道确认逻辑保留在 retrieve 后——
路由定意图、检索结果定可用材料,两者分离使「意图对但材料缺」可自然退化
(文档未命中→纯数据答)。备选「路由同时决定执行路径(检索后判定)」被否:
那需要检索完成后才能路由,融合态无法提前准备,且词表兜底与 LLM 判定的
替换点不清晰。

### D2: LLM 路由失败/低置信回退词表,保守缺省数据态

路由 LLM 失败、超时或置信低于阈值(缺省 0.7,配置常量)时回退规则词表
判定——词表命中知识触发词→知识态,否则数据态(词表没有融合态,回退态
天然保守,最坏退回 093 前行为)。回退计数入可观测。备选「低置信直接判
融合」被否:融合态双通道成本最高,拿不准时不该选最贵路径。

### D3: 融合答复用 retrieve 已检得的文档命中,不做二次检索

retrieve 节点本就双通道检索(schema + 文档);fused_answer 节点在 SQL
链路收口后执行,输入 = SQL 结果面(结果集/insight 素材)+ retrieve 阶段
文档父块命中,一次生成调用产出融合正文。备选「融合态单独再检索一次文档」
被否:同问句两次检索结果一致(缓存之外徒增延迟),且两份命中集会制造
净化键集合不一致的隐患。

### D4: 收口语义数据为刃——SQL 终态优先

SQL 通道终态非 SUCCESS(NO_DATA 哨兵/FAILED)时按数据态终态语义收口,
文档命中不顶替数据结论、不出引用(知识-qa spec 已定);文档未命中时
退化纯数据答。只有 SQL SUCCESS 且文档命中才产出融合正文。此序不可逆,
避免「文档答得漂亮但数取错了」的粉饰路径。

### D5: 融合消息形态 = 数据消息形态 + 正文换融合版 + sources 投影

消息保持既有数据面字段(SQL/rows/终态),正文位由融合生成替换,sources
由净化后正文投影(chat 契约放宽已在 delta 声明);web 复用既有渲染
(正文引用标记 + sources 面板 + 结果表),仅校验并存展示不破版,不做
新组件。净化与投影复用 068 既有实现,合法键集合取 fused_answer 下发的
父块集。

### D6: 路由 LLM 走 multi-model-routing 已有小模型档

意图判定是轻量分类任务,经既有 llm.py 配置选路由档小模型(复用
multi-model-routing 的分档机制,不新增客户端/依赖);路由调用带超时
(缺省 3s,超时即回退词表)。

## Risks / Trade-offs

- [路由 LLM 增加每问延迟(一次前置调用)] → 小模型 + 3s 超时回退;
  每次图执行路由一次(勘误:原记「同题沉淀缓存命中跳过路由」——实施期
  核实 km:ragctx 是 retrieve 节点内的检索上下文缓存,仓内不存在整答短路
  层,该前提不成立;路由与沉淀缓存无交互)
- [路由误判融合态造成双通道成本] → 置信阈值保守(0.7)+ 缺省数据态;
  误判只影响答法零副作用,trace 可回放逐例修 prompt
- [融合正文生成失败拖垮整答] → fused_answer 失败回退纯数据答正文
  (SQL 结果面已就绪),融合失败计入可观测,不使消息失败
- [sources 语义放宽引发前端存量假设破裂] → 纯数据道恒为空保持;
  web 侧以生成类型重验三态(数据/知识/融合)×亮暗两态渲染

## Migration Plan

纯代码变更无 schema 迁移;契约 description 更新走 make contracts 前端
类型再生成。回滚 = 图配置摘除 route_intent/fused_answer 节点,词表判定
恢复单源(代码保留不删)。

## Open Questions

- 融合态下 insight 段(既有数据洞察)与融合正文是否合一输出——实现期
  以「融合正文即洞察位正文」落地,若体验割裂再拆两段(不影响契约)。
