# Design: 046 SQL 投影 id 收敛

## Context

SQL_GEN_SYSTEM 是上游逐字移植资产(prompts.py 文件头例外清单制,已有 018/043
两批增量登记)。现状三条相关语义:

- 规则 3(列投影):「ID/编号列不能替代名称列(**ID 可附加**,但名称列必须
  在投影中)」——「可附加」被模型泛化为「明细该带 ID」,技术主键进投影;
- 规则 6(结果集保护):「凡 ORDER BY … LIMIT 取前 N……排序键可能并列时
  必须追加**主键等唯一列**作第二排序键」;
- 反例区:「❌ 用 ID/编号列替代名称列(……**ID 可附加**,名称列必须在投影中)」。

test_prompts.py 现钉关键句:规则 3 的「ID/编号列不能替代名称列」「❌ 用 ID/
编号列替代名称列」、规则 6 的「排序键可能并列时必须追加主键等唯一列作第二
排序键」「❌ 排序键可能并列却不追加唯一列」——这些句式在本次改动后必须仍然
成立或同步更新。

## Goals / Non-Goals

Goals:
- 技术主键默认不进投影、点名不拦;业务编号列优先作展示标识;
- DISTINCT 去重查询的排序 tiebreaker 显式例外(PG 硬约束一侧让位);
- 例外清单登记+断言同步,资产纪律闭环。

Non-Goals:见 proposal Non-goals(统计口径主键/执行层/上游其他资产/gold 重写)。

## 决策

### D1 改哪些句(最小改动面,不重写整条规则)

| 位置 | 改法 |
|---|---|
| 规则 3「ID 可附加」句 | 收紧为「**技术主键等代理键(如 `*._id`)默认不进投影,用户明确点名 ID/编号时才投影**;行标识需要编号时**优先业务编号列**;ID/编号列不能替代名称列(用户点名编号或 ID 作排序键时可附加,但名称列必须在投影中)」——保留原句尾(排序键附加语义不受影响,钉句断言存活) |
| 规则 6 tiebreaker 句 | 句尾追加「**DISTINCT 去重查询例外:ORDER BY 列必须在投影内(PG 硬约束),追加投影外主键会报错、塞进投影则去重失效——排序键只能取已在投影中的列,并列可能让位于去重**」(「必须追加主键等唯一列作第二排序键」主句不动,钉句断言存活) |
| 反例区 | 新增一条「❌ DISTINCT 去重查询追加投影外主键排序」;校准既有「❌ 用 ID/编号列替代名称列」的「ID 可附加」措辞(改「技术主键默认不进投影」) |

理由:改句不重写=改动面与回归面最小;两处主句原样保留,既有断言与 018
评审结论(名称列必须在投影/投影完备)零扰动。

### D2 为什么例外放规则 6 而不是改写规则 9

规则 9 已有 COUNT(DISTINCT 实体主键)(聚合口径);DISTINCT 明细去重+排序
的冲突点在规则 6 的 tiebreaker 句,例外就近挂靠,语义与位置一致,避免跨规则
引用。

### D3 全角标点与文本形态

规则文本为给 LLM 的提示词,新增句沿用全角标点、与上下句同形态(单引号长
字符串内 \n 分隔);不在 prompt 内使用半角括号/引号混排。

### D4 残余风险:历史成功 SQL 回写段

query_history few-shot 中已回写的成功 SQL 可能含旧形态(带 id 投影)。规则 10
已声明历史段「仅供参考口径」,且生成纪律以系统提示为准;该残余接受,不做
回写数据清洗(成本高收益低,新回写自然收敛)。

### D5 evals gold 排查口径

排查 evals/ 下 gold 是否存在「预期结果含代理主键列」的题(执行后结果集多
一列 id)。若有:登记清单、不改判 Execution Match 语义,按 gold 规范单独立项;
预期 sakila/olist gold 多为业务口径题,命中概率低。

**排查结论(2026-08-29 实施期,72 题全查)**:零需改。全部 id 出现形态为
JOIN ON/GROUP BY/ORDER BY/子查询(排序与连接侧不在收敛范围)+ 一例
sakila_003「查询所有门店的编号」SELECT store_id——问句点名编号,按新口径
「点名不拦」合法保留。

### D6 列级哨兵补全(冒烟收编):两级数据未覆盖 + 文案泛化

冒烟实测「价格最高的3个商品」(goods 表无 price 列)暴露:043 哨兵是
**表级**出口(「无支撑本问题的表」),表存在但问句所需**度量列**不存在时,
模型以 `ORDER BY id` 冒充价格排序,且 summarize 层给出不实结论
(「价格最高的是…」)。裁决:

- **根因在生成层,修哨兵语义不修下游**:规则 10 哨兵触发补全为两级——
  表级(无支撑本问题的表)+ 列级(问句所需关键信息项不存在**且无法由
  现有列合理推导**);「合理推导」豁免保留计算型指标的活路(如销售额=
  单价×数量不算缺口)。短路链 043 已建好,列级复用同一条(零新增管道)。
- **否决 summarize 层加「结果列不含问句度量不得下结论」防护**:根因修复
  后该类形态到不了 summarize;为不可达形态加 prompt 规则=死代码,徒增
  token 负担稀释其他规则的遵从度(上游 38 变更经验:规则越少越硬)。
- **否决机械校验**(ORDER BY 列须与问句词面匹配之类):「错误但存在的列」
  (用 id 冒充价格)是语义判断,机械规则既漏报又误报;LLM 判断+哨兵出口
  是该层的正确工具。
- **文案泛化**:`_NO_DATA_ERROR` 「未找到与问题相关的数据表」→「未找到
  回答该问题所需的数据」(列级下「数据表」措辞不实);api 兜底
  (chat/service.py)、web 兜底(assistant-card)镜像同步,三处同串;
  does-not-exist 喂回「所引用的表」→「所引用的表或列」。
- chat 主 spec 场景中的文案示例为说明性引用,归档 sync 时随手对齐,不另
  开 delta。
