# 068-doc-answer-citations 设计

## Context

- 文档道链路:`retrieve` 条件分流 → `doc_answer`(无 SQL 面)→ api `_stream_finalize` 落库。
  命中的父块以 `doc_hints: [{source_ref, content}]` 进提示词(`nodes.py:429`,截 top-5 /
  1500 字符),正文与来源之间**没有任何机器可校验的连接**。
- 本仓已有一次同类成功实践:057 的数值白名单审计——确定性纯函数、在产出后收口、
  宁剥离不编造、不重试 LLM、不阻断主链路。引用净化是同构问题,应当复用同一设计语言。
- 双进程现实(ADR-002):证据注入方在 api(持主键与凭证),标注消费与净化在 agent
  (零凭证)。任何"靠两边共享一个自增序号"的做法都需要跨进程状态同步。

## Goals / Non-Goals

**Goals:** 用户看到的每一处"出处"都可定位到本轮真实下发过的文档块;系统不产出编造出处,
且历史引用不随文档改名而腐坏。

**Non-Goals:** 见 proposal。特别地:**不判定引用是否恰当**,只判定引用是否存在。

## Decisions

1. **引用键在 api 铸造,经 `doc_hints` 纯增字段下发**
   父块主键只有控制面可见。Agent 面若自行派生需要拿到主键——把 UUID 递出控制面是
   无谓的敏感面扩大(050 ID 暴露治理的口径正是反向)。故 agent 只见键,不见主键。

2. **键 = 可读前缀 + 定长哈希后缀,不用序号 `[1] [2]`**
   序号方案的两个硬伤:①序号由"本轮命中顺序"决定,而注入段与来源列表在不同进程、
   不同时机构造,共享序号分配器等于新增跨进程状态;②命中集变化(重跑、补历史、
   top-5 截断口径调整)会让同一文档在不同轮次拿到不同序号,历史消息回放即错位。
   哈希后缀由主键确定性派生,一次消掉这两个问题,并让"数组顺序不承载语义"成为
   可以写进契约的性质而非口头约定。
   前缀保留可读性(人在正文里看到 `【员工手册-K7A4】` 知道在说哪份文档),
   且模型改写前缀不致命——净化有后缀兜底(见 D3)。

3. **未命中降级为纯文本,不删除**
   删除会把括号连同内容一起抹掉,句子结构受损;更糟的是它把"编造出处"静默改写成
   "没有说过",读者与运维都无从察觉发生过净化。剥掉括号标记、保留括号内文字,
   使该表述降级为一句普通陈述——与 057「整句剥离、不整段拒绝」同取向,
   本仓在净化类缺陷上的一致口径。
   匹配两级:全等 → 末段后缀全等。第二级专治模型省略/改写人读前缀
   (把 `员工手册-K7A4` 写成 `手册-K7A4`)这一高频真实形态。刻意不做模糊匹配:
   净化器一旦"猜测",就重新引入了它要防的那类错误。

4. **`sources` 由净化后的正文单向投影,而不是"正文与列表各自构建"**
   上游的做法是两处各自派生同一条键、再靠确定性对齐——仍是两个构建方。
   本仓让来源列表 = 扫描存活标记得到的键集合,再按本轮命中集回填元数据。
   结果是**构造上一致**:不可能出现"列表有条目而正文无标注"(幽灵条目),
   也不可能"正文有标注而列表查不到"(死锚点)。代价是净化后多一次正文扫描
   (O(标记数) 纯字符串),相对一次 LLM 调用可忽略。

5. **净化落点在 agent 的 `doc_answer` 尾部,与 057 同位**
   答案文本的确定性净化在本仓已有同层先例与同类测试位;放到 api 会让"发给用户的正文"
   与"落库的正文"分两次处理,极易漂移。净化在 api 护栏 `filter_output` 之前完成,
   保证下发与落库是同一串(与 `result` 帧由 `_out(outcome)` 单点构建的既有纪律一致)。

6. **合法键集合取自截断前的完整命中集**
   净化用的合法集 MUST 大于等于提示词里实际出现的集(截 top-5 / 1500 字符之后)。
   若用截断后集合,一个真实引用可能因为在展示列表里被裁掉而被判成编造——
   那是净化器自己制造的假阳性,比漏判更糟。

7. **零新流式事件型**
   文档道 summary 现状是单帧完整下发,`sources` 随既有 `result` 终态帧一起到即可;
   为"提前显示来源条"新增 `references` 事件是扩契约换微弱体验收益,不做。

## Risks / Trade-offs

- [模型一条都不标注 → `sources` 为空] → 行为等同现状,不惩罚、不重试;
  把**标注率**计入 trace 观测,低标注率再回到 prompt 纪律层解决(不引入判官)。
- [哈希后缀碰撞导致引用指向错文档] → 定长 4 位 36 进制基数约 168 万,
  单租户文档块规模下概率可忽略;碰撞的可发现成本高(来源区展示文档名,人一眼可辨),
  属明确接受的取舍,与上游同结论。若语料规模上台阶,加长后缀即可,键格式向后兼容
  (净化按"末段"匹配,不写死长度)。
- [改名后正文里的旧前缀看着不一致] → 键不变故锚点不失效;展示名取消息落库时的
  `sources` 快照,**不回查文档表**——历史轮次展示"当时叫什么"是更正确的语义。
- [净化把用户自己输入的 `【…】` 文本剥掉] → 净化只作用于本轮模型产出的答案正文,
  且只剥"形如键"的标记(需含 `-` + 末段哈希形态);普通中括号内容原样保留。
  该形态判定规则须有回归用例。
- [新增字段对老客户端不兼容] → 纯增字段;`?? []` 兜底,与既有
  `pending_tool_calls ?? []`(R1-D3)同一处置纪律。

## Migration Plan

无数据迁移。发布顺序:先合净化与键派生的纯函数 + 失败测试(测试先行),再接线;
前端来源区与角标可在后端字段就绪后再发(字段缺失时按现状渲染纯文本,不报错)。
回滚 = 停止下发 `sources` 并还原纪律段;正文里的 `【…】` 标记退化为可读文本,
不产生不可逆状态。历史消息无 `sources`,前端按空列表渲染(不报错、不回填猜测)。
