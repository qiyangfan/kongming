# 068-doc-answer-citations 提案:文档道引用契约(稳定键 + 编造净化)

## Why

文档知识道(`doc_answer`,024)的回答溯源目前是**纯提示词请求,零数据、零校验**:

- `rag/documents_service.py:124` 只回传 `{source_ref, content}`——父块主键 UUID 在跨进程时
  被丢掉,没有任何稳定标识进入响应;
- `source_ref` 由 `chunker.py:101,112` 拼成 `{文档名} §{父块序号}{标题}`,**父块与其全部子块
  共用同一串**,且随文档改名或重新分块整体变化;
- `doc_prompt.py:11` 规则 2 要求模型句末标注 `[文档名 §段落]`,但没有任何东西保证它标得对;
- `contracts/openapi.json` 中 `citation` **出现 0 次**;`ChatQueryOut`/`SessionMessageOut`
  无 sources 类字段;`apps/web` 无角标、无来源面板、无正文→原文定位。

### 真正的缺陷不是"没有来源面板",而是**编造的来源无人拦截**

同一份 `DOC_ANSWER_SYSTEM` 规则 1 已经明文禁止编造事实,而 057 为"编造的**数字**"建了
确定性白名单审计并逐句剥离(已归档、全绿)。**同一可信面上,数值有防线,引用没有**——
模型写一个根本不存在的 `§3 库存政策`,系统会原样落库、原样展示给用户。对 2C/2B 问数与
知识问答产品,伪造引用的危害不低于伪造数字(它把臆测包装成"有出处的事实")。

另一半代价是**引用腐坏**:`source_ref` 里编进了文档名与段落标题,文档改名或重切块之后,
历史消息正文里那些方括号文本全部指向不存在的段落,而正文是自由字符串,无从校验也无从修复。

上游问答线在同一问题上收敛到一套很轻的机制,其核心不是"加个来源列表",而是
**用确定性派生键把"注入证据的一方"与"构建引用列表的一方"解耦**,再做一次零模型的
事后净化。本变更移植该机制的**逻辑**(键派生 + 未命中降级净化 + 顺序无语义),
按本仓双进程边界与 057 的既有收口点重写,不复制其代码。

## What Changes

1. **稳定引用键(确定性派生,api 侧铸造)**:文档道检索命中时,由父块主键派生
   `citation_key` = 可读前缀(文档名去扩展名)+ 定长哈希后缀(如 `员工手册-K7A4`),
   随 `doc_hints` 下发给 Agent 面。键 SHALL 满足:
   - 同一父块在任何一次召回中派生结果**恒定**,与命中名次、命中路数、请求次序无关;
   - 由主键派生,故**改名/重切块不改变键**,历史引用不腐坏;
   - 注入证据的一方(api)与构建引用列表的一方可各自独立派生即对齐,
     **数组顺序 SHALL NOT 承载对齐语义**。
2. **正文标注改为引用键**:`DOC_ANSWER_SYSTEM` 纪律段要求句末标注 `【citation_key】`,
   并明文禁止输出 `【来源：…】` 形态、禁止自造未下发过的键。
3. **确定性净化(零模型调用)**:答案产出后扫描全部 `【…】` 标记,两级匹配——
   全等于合法键 → 保留;末段哈希后缀全等于合法键后缀 → 保留(容忍模型改写人读前缀);
   否则 **降级为纯文本**(剥掉括号、保留括号内文字,不改写句子其余部分)。
   合法键集合 SHALL 取自**截断前**的完整命中集(避免条目上限误杀真引用);
   合法键为空(闲聊/未覆盖/降级路径)时整体跳过净化。被剥标记数 SHALL 计入 trace。
4. **结构化来源上契约**:响应与落库携带 `sources[]`,每项含
   `citation_key` / 文档名快照 / `source_ref` / 段落序号。
   **`sources` 是净化后正文里存活标记的投影**——由正文单向派生,故构造上不可能出现
   "列表有条目而正文无标注"或反之的幽灵不一致。文档名随消息落库为快照,历史回放
   SHALL NOT 回查文档表。
5. **前端呈现**:答案正文渲染角标,来源区可展开;点击角标定位到该消息来源条目并高亮,
   同一条消息内命名空间隔离(同一文档在多轮被引用不串)。按前端宪法走
   shadcn/ui + token,暗色同步给值。
6. **边界不变**:净化是纯字符串函数,落在 Agent 面 `doc_answer` 尾部
   (与 057 `numeric.audit_summarize_output` 同一收口位置);键铸造与 `sources` 构建、
   落库在控制面。Agent 面零凭证不变。

## Non-goals

- **不做"引用是否真的支撑该句"的语义核验**(主张分解 / LLM 判官)。本变更只保证
  **不出现凭空键**,不保证引用恰当——后者已在 016/057/058 三度书面否决,理由依然成立。
- **不做文档预览、下载密级、预签名 URL、PDF 分页定位**。那是文档资产管理面
  (`/admin/rag` 已有详情),本变更只做对话内溯源。
- **不做子块(chunk)级引用粒度**:父子结构下答案依据是回填的**父块全文**,引用到父块
  即与注入粒度一致;引到子块需同时改证据注入与展示口径,收益不成立。
- **不给 SQL 道加引用**:数据问答的溯源是已展示的 SQL 与 EXPLAIN 计划,
  伪造一套"数据引用键"是画蛇添足。
- **不改终态与状态机**:SUCCESS/REJECTED/FAILED/NO_DATA 四态语义零变动;
  未覆盖回答路径不产 `sources`。
- **不新增流式事件型**:`sources` 随既有 `result` 终态帧下发(文档道 summary 本就是单帧),
  `query-streaming` 契约零改动。
- **不做引用重排/去噪模型、不做引用数上限管理台**。

## Capabilities

### Modified Capabilities

- document-rag:「chunk 级 citation」从 SHOULD 标注升为**确定性引用键 + 编造净化 +
  结构化来源上契约**的 MUST 行为,并明确顺序不承载对齐语义、改名不破坏历史引用。
- chat:问答响应与消息历史 SHALL 携带该轮结构化来源(仅文档道产出非空),
  且正文存活标记与来源列表 SHALL 一致。

## Impact

- **落点**:`apps/api/kongming/rag/documents_service.py`(键铸造与透出)、
  `rag/router.py` 或 `/internal/rag/retrieve` 响应段(增 `citation_key`,纯增字段)、
  `apps/agent/kongming_agent/graph/citations.py`(新增:派生比对 + 净化纯函数)、
  `graph/nodes.py:doc_answer`(接入净化)、`graph/doc_prompt.py`(纪律段增量,
  按 prompts.py 头部的资产变更纪律登记)、`chat/service.py`(sources 投影与落库)、
  `chat/models.py`、`apps/web`(角标渲染 + 来源区)。
- **契约(ADR-005)**:`ChatQueryOut`/`SessionMessageOut`/`MessageResultOut` 与内部
  retrieve 响应均为**纯增字段**,无字段删除或语义变更;须 `make contracts` 并提交
  `contracts/openapi.json` 与生成的前端类型。
- **Schema(ADR-004)**:**无迁移**。来源随既有 `chat_message.result_json`(TEXT,
  承载 columns/rows/insights/stats 的同一条序列化通路)落库;引用键由主键派生,
  `document_chunks` 无需新列。已核对 baseline `0001_baseline.py:174-197`。
- **信任边界(ADR-002)**:Agent 面仍零凭证零 DB 配置——它只接收键字符串并做纯文本净化;
  主键不出控制面。
- **护栏顺序**:净化在护栏 `filter_output` 之前完成(先剥编造标记,再过输出护栏),
  避免被剥标记以残括号形态进入输出文本。
