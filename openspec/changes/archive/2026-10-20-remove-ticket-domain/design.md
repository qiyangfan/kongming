# Design

## Context

当前 ticket 专属行为分布在配置与启动校验、工具注册/分发、ticket 网关适配器、RBAC 权限种子、mock 服务和测试中；工具网关仍被 websearch 与通用 HTTP 连接器使用，不能随 ticket 一起移除。权限定义采用启动时只增只补的种子策略，`sys_role_permission.permission_id` 对 `sys_permission.id` 有外键约束；工具审计则共享 `sys_tool_audit`。路线图此前将 ticket 记为等待真实凭证，并认定无工程欠债；本次提案重新评估的是“是否继续为一个尚无真实系统适配对象的专用工具域承担产品与维护成本”，不否认旧实现已完成其既定范围。动机与变更范围见 [proposal.md](proposal.md)，目标行为见本变更的 `tool-gateway` delta。

## Goals / Non-Goals

**Goals:**

- 让 ticket 从运行时注册、执行、授权和部署配置中完整退役，同时保留其余域及通用出站治理。
- 清理两个 ticket 权限点及其角色绑定，不删除工单历史审计。
- 保证旧工具名和待确认创建请求在新版本中 fail-closed，不触发外部请求。

**Non-Goals:**

- 不实现 Jira、ServiceNow 等真实供应商适配，不自动把旧配置或权限转换成 HTTP 连接器配置。
- 不改造通用 HTTP 连接器、工具网关架构或其他域的授权/配额策略。
- 不改变 API schema、数据库 schema、Agent 回调边界或历史审计格式。

## Decisions

### 1. 只删除 ticket 专属切片，保留共享网关

删除 ticket 的配置字段与校验、启动告警、manifest/执行器/策略装配、三个工具定义与客户端、独立配额、权限种子、mock 服务及对应测试。保留 websearch、通用 HTTP 连接器和 `tool-gateway` 的通用注册、审计、确认、限流与出站策略。

**理由：**共享网关仍有多个消费者；删除整个网关会扩大变更并破坏现有能力。相比仅隐藏工具或保留未使用适配器，移除完整 ticket 专属切片可消除无调用价值的代码与配置。

**考虑过的替代方案：**保留 ticket 代码但默认不配置。该方案仍维护一套只有 mock 可验证的协议、凭证和 RBAC 面，且会继续让部署者误以为配置后即可接入真实工单系统，因此不采用。

### 2. 不自动迁移到通用 HTTP 连接器

不把 `KM_TICKET_*` 变量转换成租户 HTTP 连接器，也不把 `tool:ticket:*` 授权转换成 `tool:http:call`。需要替代能力的租户须显式创建连接器、配置凭证/出口策略，并单独授予权限。

**理由：**连接器是租户级配置而 ticket 是部署级服务凭证；授权粒度和信任边界不同。自动转换会扩大权限，且无法推断真实服务端点是否遵守 mock 的三端点协议。

**考虑过的替代方案：**将 ticket 工具包装成三个预置 HTTP 连接器。其工具名、参数/返回观察、创建确认与当前通用连接器契约不一致，并保留了被退役的协议方言，因此不采用。

### 3. 使用精确范围的数据迁移清理 RBAC，不触碰审计

新增 Alembic 数据迁移，只针对 `tool:ticket:search` 与 `tool:ticket:manage`：先删除引用这两个权限 ID 的 `sys_role_permission` 绑定，再删除对应 `sys_permission` 行。迁移不扫描或删除 `sys_tool_audit`，也不改动任何其他权限或角色。

**理由：**种子注册表是权限点的唯一代码定义，但启动种子只增不删；仅删除代码种子会使数据库继续暴露过期权限。精确迁移能消除失效授权入口，同时保留审计证据。此迁移不新增或修改 schema（ADR-004）。权限处理遵循现有 RBAC 边界（ADR-003）；控制面仍独占任何服务凭证，Agent 信任边界保持 ADR-002。

**回滚约束：**迁移前必须做数据库备份。降级代码前恢复该备份，才能完整恢复自定义角色绑定；只回滚应用并不能找回已删除的绑定。迁移不维护永久影子权限表，以免为仅用于回滚的数据引入新的运行期存储。

### 4. 先停旧 API 实例，再执行权限清理

发布顺序为：备份数据库和部署配置；滚动到不含 ticket 权限种子与执行路径的新版本并确认旧 API 实例已全部退出；移除/撤销部署中的 `KM_TICKET_*` 服务凭证；执行权限数据迁移；验证新版本无 ticket 工具、权限点和出站请求。

**理由：**旧版启动种子会重新插入缺失权限，并为 `SUPER_ADMIN` 补齐代码中定义的权限。若旧 API 实例仍运行，在迁移后重启会再次创建 ticket 权限。

### 5. 保持既有非 ticket REST 契约不变

ticket 工具通过动态工具注册暴露，不属于 OpenAPI REST 契约；移除它不更新 `contracts/openapi.json`，也不需要改变 Agent/API 回调协议（ADR-005）。审计表中的历史 ticket 记录保留。新版本对遗留工具名及待确认创建请求拒绝执行并按既有工具调用路径审计，不发送出站请求。

**考虑过的替代方案：**为兼容旧工具名保留拒绝用的 ticket 适配器。其仍会留下票据域注册/授权面，扩大持续维护边界；通用“未注册工具拒绝”路径已能安全处理陈旧调用，因此不采用专用兼容层。

## 方案对比

| 维度 | 当前：保留专用 ticket 域 | 选定：退役专用域，必要时显式使用通用连接器 |
|---|---|---|
| 复杂度 | 维护部署配置、条件注册、专属执行/字段映射、独立权限/配额、确认和 mock 测试 | 删除 ticket 专属路径，复用既有连接器治理；不增加新的抽象 |
| 性能 | 已配置时仍是一轮外部 HTTP 请求；字段 allowlist 会收窄返回观察 | 移除后无 ticket 请求成本；若改用通用连接器，响应是受大小上限约束的通用文本，LLM token 可能多于卡片结果，需由连接器配置者控制响应体 |
| 兼容性 | 保留 `ticket_*` 工具名、旧环境变量、独立权限和标准化卡片 | 对现有调用方是明确破坏性变更；不做静默转换，迁移者需重建连接器与授权 |
| 测试 | 维护 mock 协议、票据卡片与确认/权限/配额的专属覆盖 | 删除该能力的专属行为测试，新增旧工具零出站及 RBAC 清理验证；通用 HTTP 覆盖继续保留 |
| 迁移成本 | 无变更成本，但需要真实 API facade 遵循 mock 的三端点协议 | 删除旧环境配置并撤销凭证，执行两项 RBAC 数据清理；需数据库备份以恢复自定义角色绑定 |
| 长期维护 | 即使无真实消费端也要跟进专用协议；真实 Jira/ServiceNow 仍需外部 facade/适配 | 不维护无消费证据的专用协议；未来出现明确需求时，按具体目标设计显式连接器或真实供应商适配 |

此选择不主张有可量化的吞吐收益；主要收益是减少没有已验证消费对象的专属代码、配置和授权面。若路线图中“等待真实凭证”的前置条件已发生变化，应在 apply 前重新核实部署是否正在使用 `ticket_*`，而不是默认为没有调用方。

## Risks / Trade-offs

- **依赖旧工具的部署会失去工单问答与创建能力** → 发布前盘点 `KM_TICKET_*` 配置和调用方；在发布说明中列明工具名移除；需要替代能力时由管理员显式配置通用连接器与授权。
- **旧服务凭证可能在系统移除后仍有效** → 发布时从控制面环境变量/密钥管理中删除并按部署凭证流程撤销；不把凭证值写入迁移或日志。
- **数据迁移后直接回滚会丢失自定义角色绑定** → 强制先备份；回滚应用前恢复数据库备份，或由管理员基于授权清单重建绑定。
- **在途 `remove-siku-integration` 工件仍将 ticket 写作剩余域示例** → 两个变更合并/应用前协调改正该示例；本变更不修改该并行工件。

## Migration Plan

1. 确认部署不再需要 ticket 工具；备份数据库，并盘点旧环境变量、服务凭证和角色授权。
2. 发布移除 ticket 代码与权限种子的版本，等待所有旧 API 实例退出。
3. 删除旧 ticket 环境变量并撤销相应服务凭证；运行只清理两项权限点及绑定的数据迁移。
4. 验证 ticket 工具不进入注册/注入集，直接调用和在途确认均被拒绝且零出站；确认 websearch、HTTP 连接器及历史审计保持可用/完整。
5. 若回滚，先恢复迁移前数据库备份，再部署旧版本；不可只回滚代码后假定自定义角色授权已恢复。
