# Design: add-chat-turn-cancel

## Context

动机见 proposal.md「Why」。与本设计直接相关的现状:

- **三跳中继**:浏览器 ←(SSE)← 控制面 ←(SSE)← Agent 面。控制面为每轮
  起一个后台消费任务(断线续存:前端断开不影响该任务),终态帧在 assistant
  消息落库之后才入队。
- **Agent 面的流式生成器**直接以 `async for … graph.astream(...)` 驱动图执行
  并逐帧 `yield`;常规问答图与工具调用内核两个流式入口同形。
- **「停止」只是脱离接收**:前端中止读取,后台任务照常跑到终态。这是刻意的
  设计——刷新、断网、切会话都不该丢结果——不能为了取消而破坏它。
- **trace_id 是单源**:请求级生成(或取入站头),响应头 `X-Trace-Id`、该轮
  模型用量、审计、落库消息同值;运行时已有,只是未进 OpenAPI 声明。
- **消息状态四态**(SUCCESS/FAILED/REJECTED/NO_DATA),CHECK 约束收口;
  质量面以「全部 assistant 消息」为轮次范围做统计。
- **约束**:单节点部署形态;Agent 面零凭证(ADR-002);领域代码零框架依赖、
  外部能力经 Protocol 反转;契约生成(ADR-005);schema 演进走新迁移(ADR-004)。

## Goals / Non-Goals

**Goals:**

- 用户点停止,这一轮就真的停:Agent 面停止图执行,此后不再发起模型调用与
  工具调用。
- 历史如实:该轮留下一条「已取消」,不留半截结果,也不留完整回答。
- 断线续存零回归:刷新/切会话/断网的行为逐字不变。
- 取消路径的两段(Agent 面停止、控制面收敛)都能用项目惯用的进程内测试
  确定性断言。

**Non-Goals:**

- 不追求「Agent 面已崩溃或网络分区」下的即时停止——此时靠断开连接兜底,
  该路径只做手工冒烟。
- 不改变 Agent 面的终态帧契约,不为取消新增流式事件类型。
- 不处理「等待写工具确认」的轮次(没有在途执行)。

## Decisions

### D1 让 Agent 面停下来:显式中止端点,而不是只靠断开连接

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| 断开即取消 | 控制面取消本地消费任务→关闭到 Agent 面的流→Agent 面的响应任务被服务器取消 | Agent 面零改动;但正确性挂在 Web 服务器对「客户端断开」的处理上,项目惯用的进程内测试无法确定性复现,要起真实端口才能测;Agent 面不知道自己被取消,无从记录;流尚未开始时断开是否被察觉取决于时机 |
| **显式中止端点(选)** | Agent 面把图执行放进自有任务并按 trace_id 登记;端点取消该任务 | 两段都能进程内确定性测试;Agent 面可记录被取消的事实;与当初留下该独立变更时的判断一致。多一个内部令牌端点 |

断开连接没有被弃用:它是 Agent 面不可达时的兜底(见 D8)。显式端点是主路径,
因为它把「停下来」从「连接的副作用」变成「一条可以测试的约定」。

实现要点:生成器不再直接驱动图,而是排空一个帧队列;图执行在自有任务里把
帧放进队列(原有的异常收敛原样搬进该任务);任务结束即注销登记。之所以用
自有任务而不是取消响应任务本身,是为了不与 Web 框架的任务组语义纠缠。

### D2 取消的终态由控制面单方面落库

备选是让 Agent 面取消后在流上补一帧「已取消」终态,控制面照常收敛。不选:
那要给 Agent 面的终态契约新增一个 verdict、给控制面的状态映射扩一支,而且
取消与断流竞争时这一帧未必送得到。

选定:控制面只要发现「本轮已被请求取消」且没有拿到正常终态,就自己写已取消
行。Agent 面的终态契约零变化,取消结果不依赖它的最后一帧。

### D3 轮次标识复用 trace_id

`X-Trace-Id` 响应头运行时已有,且与用量、审计同值;把它写进 OpenAPI 声明
即可,不新造轮次编号,不动 SSE 帧协议。

入站 `X-Trace-Id` 头本就可被调用方指定,所以登记以「用户 + trace_id」为键:
他人即使指定同一个 trace_id,既查不到也取消不了别人的轮次(404 同形)。

### D4 新增第五态 CANCELLED

- **复用 FAILED**:把用户主动放弃算成系统失败,污染失败率与质量台账。否。
- **取消后删除本轮 USER 消息**:破坏「控制面每一轮都写终态行」这个不变量
  (页面恢复轮询依赖它),该轮已发生的模型用量也失去可关联的消息。否。
- **新增 CANCELLED(选)**:与当初加「无数据」第四态同法——一次迁移放宽
  CHECK。代价是每个按状态统计或分支的地方都要表态;本变更的表态见 D6、D7。

### D5 在途轮登记放进程内存

单节点部署形态是既有前提(「SSE 跨节点广播」因此被否决)。进程内结构零新
依赖、测试不需要容器。若将来多实例,取消请求可能打到另一个实例而得到 404
——记为限制,不为它引入共享登记。

### D6 质量观测面整体不计已取消轮次

轮次范围的子查询统一排除 CANCELLED:汇总、趋势、明细、同会话串联、导出
同源,管理台前端零改动。已取消轮次仍可在会话历史、按 trace_id 的用量时间线、
按消息标识的节点轨迹查询里追溯。

备选「新增取消率/取消位置维度」是新的产品面,不在本变更;是否值得做,留到
问答时延优化立项时评估。

### D7 已取消行是裸终态行,写入前按 trace_id 查重

与「Agent 面不可达」的 FAILED 行同形:`summary` 承载取消说明,`result_json`
显式 `artifacts=[]`(防止回显时重算出文档卡),携带取消前已收集的节点轨迹。
不走正常终态管线,避免把半截 SQL 或半截摘要落库。

写入前按 trace_id 查 assistant 行:已存在说明取消与完成几乎同时,此时不写,
按「已正常结束」返回。同一轮至多一条 assistant 应答。流式的 FAILED 行同样
带 trace_id,这道查重对全部流式终态行有效;采用已有行时结论词还原为响应
口径(落库 REJECTED 即 BLOCKED)。

### D8 控制面的取消编排

1. **登记**:后台消费任务启动时登记(用户, trace_id)→句柄,任务结束即注销。
2. **取消**:置取消标记 → 通知 Agent 面(限时;失败只记日志)→ 等本轮收敛
   (限时)→ 超时才硬取消本地任务。常规路径里 Agent 面会在毫秒内结束流,
   根本走不到硬取消。
3. **消费任务的收敛**:流结束或失败后,若「取消标记已置且没有正常终态」→
   写已取消行,否则按既有规则收尾(result 或 error)。收尾(落库 + 终态帧)
   独立成任务,一旦开始就不被请求取消打断:硬取消落在收尾段时等它做完,
   本轮终态以收尾结果为准。每种收尾都记下收敛结果,取消发起方据此回答。
   取消标记未置时被外部取消(如进程关停)→ 原样上抛,不伪造终态。
4. **竞争**:已收到正常 result 之后才到达的取消不取消任务,等它落库完按
   「已完成」返回。

取消标记在流阶段置位时,取消优先于失败收敛(同一轮流以失败告终,结果是
「已取消」)。流已结束、收尾已开始后才到达的取消不改写终态,按「已结束」
返回——失败收尾落下的 FAILED 行不会被已取消行叠加。

### D9 文案的诚实边界

取消不撤回已经发出的工具调用(含 SQL 执行)。所以成功提示固定带上「已开始
执行的操作不会被撤回」。写类工具的执行记录在工具台账里仍然可查。

## Risks / Trade-offs

- [单节点前提:多实例下取消可能 404] → 记入 HANDOFF;多实例部署是该既有
  否决项的重开条件,届时一并处理。
- [Agent 面不可达或挂起时靠断开连接兜底,该路径无自动化测试] → 列为手工
  冒烟项(停掉 Agent 面后点停止)。
- [响应头返回前的短窗口内点停止不保证取消] → 规格已立:按断线续存如实说明。
- [控制面重启丢在途轮] → 与现状一致(后台任务随进程消亡),恢复轮询超时后
  按既有口径呈现。
- [被中断的那次模型调用不产生用量行] → 已知限制;节点轨迹如实反映取消位置。
- [滚动部署时旧前端读到 CANCELLED 行] → compose 三端同发。预计旧前端会把它
  当普通结果卡呈现取消说明而不会崩溃(未实测,部署时不保证旧前端兼容)。
- [多一个内部端点] → 与既有问答端点同一道内部令牌闸,不面向用户流量。

## Migration Plan

- **顺序**:迁移 → api 与 agent → web。迁移只放宽约束,对旧代码无感。
- **回滚**:应用可独立回滚(取消端点消失;前端停止按钮须同步回到旧文案,
  否则会谎称可取消)。迁移回滚前必须先处理 CANCELLED 行(删除,或改写并
  人工核对),否则 CHECK 约束会拒绝降级。

## Open Questions

- 等待本轮收敛的上限(拟 5 秒)与通知 Agent 面的超时(拟 3 秒):部署常量,
  实现期可按实测调整,不影响规格与任务拆分。
