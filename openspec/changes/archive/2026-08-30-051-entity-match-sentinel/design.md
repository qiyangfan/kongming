# 051-entity-match-sentinel 设计

## Context

立案调查结论(证据见会话记录):失败 SQL 并未违反规则 10 的字面条款——
表名列名全部真实来自可用表结构段,失守点在「该段没有支撑本问题的表」的
**表级判定**:"支撑"从未被定义,模型把「goods 可以被 COUNT、create_by 可以
当分组键」当成了支撑依据。旁证:模型自己的洞察都在说「分类值为账号或
UUID,不符合常规分类命名规范」——它知道答案畸形,却没有任何判据支持它
弃答。query_history 中同问句的硬凑 SQL(11:45 落库)会作为历史成功 SQL
参考喂给后续同题生成,构成自我繁殖环路(041 中文别名自我繁殖同款)。

## Goals / Non-Goals

Goals:表级哨兵判据操作化(实体核对)、对位反例点名、负例评估回归守护
(smoke 闸)。Non-goals 见 proposal(确定性门禁/回写策略/understand 改造
均不采,理由见 D2)。

## Decisions

### D1 判据落点:generate 提示词,方法论循 046 实证结论

046 的实测结论是本设计的方法论基石:**抽象纪律条款对 LLM 不稳定,点名
自我合理化形态+对位反例才稳定(3/3)**。故:

1. 规则 10 增补实体核对子句——把「支撑本问题的表」操作化为可执行检验:
   问题核心业务实体(具体名词)必须能在表说明或列语义中找到对应;并把
   两种典型自我合理化形态点名禁止(量词泛化:「库存数量→对任意表 COUNT」;
   维度错配:「任意文本列→问题里的分类」)。
2. 反例清单追加对位反例——用本次实证失败的原型(问门店影片分类库存、
   表只有名称/创建人,却 SELECT create_by AS category, COUNT(*))原样
   钉死,与 046 的「价格最高按名称排序」反例同构。

### D2 否决的备选:确定性拒答门禁与 understand 前置实体抽取

召回相似度分数跨数据源不可校准,阈值拒答产生**不可恢复的假 NO_DATA**
(用户明明有数据却被拒,且无任何出口);词面重合判定过不了同义改写
(「租赁」vs「出租」)。understand 节点抽取实体前置判重,是在 generate
之外再造一层 NLU 判决——两处判决必然漂移,且同样无法避开「相关与否本质
是语义判断」这一事实。结论:判据单点留在 generate,以负例评估守护;
这正是大厂 NL2SQL 产品(拒答策略)的共同取舍——拒答宁可漏杀不可误杀。

### D3 负例评估形态:expect_no_data(与 expect_reject 分形)

NO_DATA 是**业务终态**(HTTP 200+success=False+verdict=NO_DATA+SQL 空
=哨兵短路零执行),与 expect_reject 的 HTTP 4xx 拒绝(fail-closed)不同形,
混用会污染语义。新形态断言四要素:success=False、verdict==NO_DATA、
SQL 为空(零执行硬断言)、由断言保证 pass(同拒绝用例口径:不计 strict
防虚增)。default.yaml 新建负例集:本案例原型(smoke,进第一道闸)+
一个泛化变体(全量集),守护泛化性不止于背题。

### D4 污染清理:评估重复性口径的既有 runbook,本次执行

query_history 同题硬凑沉淀会经 few-shot 喂回,评估前必须清理(README
「评估重复性口径」已载明;041 同教训)。清理范围以 question 精确 LIKE
匹配两条硬凑/相关行,不动其他历史。生产形态的防繁殖机制(回写策略)
属独立演进,不在本次(见 proposal Non-goals)。

## Risks / Trade-offs

- [判据仍属 LLM 自觉,理论上可再失守] → 负例评估(smoke 闸)把失守变成
  显性回归;046 实证该形态可达 3/3 稳定,且这是不引入假 NO_DATA 风险的
  唯一落点。
- [反例清单增长推高 prompt 长度] → 单条约 120 字,prompt 总增量 <2%;
  反例即资产(046 同款取舍)。
- [负例只覆盖 default 库] → 判据是数据源无关的通用检验,负例集只是
  抽样守护;sakila/olist 正例集同时守护「不误伤正常生成」。

## Migration Plan

无 schema/契约变化;prompt 生效需重启 agent 进程。回滚=还原提示词与
评估文件,无数据影响(污染清理为一次性运维动作)。
