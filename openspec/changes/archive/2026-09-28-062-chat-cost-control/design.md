# 062-chat-cost-control 设计

## D1 为什么用「速率 + 配额」双闸,而不是单一机制

速率闸(分钟级)防突发:一次误操作、一次前端重试风暴,分钟级就能打满;
配额闸(日/月)防累积:限速 60 次/分钟仍意味着单用户单日 8.6 万次调用。
两者覆盖面正交,缺一个就存在可被稳定利用的缺口。仓内已有两个对应轮子
(`RedisRateLimiter` 与 `billing.check_quota`),本变更是接线而非新建。

## D2 fail-open 与 fail-closed 的分界(与既有口径一致性)

判定标准:**限流是配额保护层,不是安全闸**。安全闸由权限点 / 租户隔离 /
SQL 防火墙各自独立承担(这三层都不依赖 Redis)。因此:

- 速率闸:存储不可用 → fail-open 放行 + error 级日志。与
  `toolcall/ratelimit.py` 现行注释口径逐字一致,不放宽也不收紧。
- 配额闸:存储不可用 → fail-closed 拒绝 + 落审计。理由:放行的代价是
  不可归因地烧 token,且配额读数只有一个来源(控制面库),它不可读时
  系统本就处于异常态。与 034 `/v1/chat/completions` 现行超额 429 语义
  同向。

这一分界必须写进 spec,否则实现侧会默认"限流类都 fail-open"而把配额也
一起放开。

## D3 公开嵌入面的限流维度:为什么必须新增 (bot_key, ip)

匿名端点没有 user_id、没有 tenant 头、没有 api-key。可用主轴只有两个:
助手标识(`bot_key`,防单个助手被打挂)与客户端 IP(防单源刷全站助手)。

IP 必须取 `ClientIpMiddleware` 的 contextvar 而非请求自带头:该 contextvar
的值经 `--proxy-headers --forwarded-allow-ips` 约束为可信代理链解析结果,
客户端自造 `X-Forwarded-For` 不改变它。若直接读请求头,限流键可被任意伪造,
等于没有限流。

局限(如实记录):NAT/企业出口共享 IP 会误伤同源多用户。缓解方向是按
`bot_key` 维度的阈值给得更宽,并对误伤提供 429 响应头说明;精确到人需要
嵌入方传身份,属产品决策,不在本变更。

## D4 配额计数的数据来源与零 schema 变更的边界

034 已为网关头建好配额表与判定函数。问答面的"已用量"优先从既有
`sys_llm_usage` 按窗口 count 派生,不新增用量表——避免 055 成本对账
之外再造第二份账。

代价是该 count 落在持续增长的表上。因此本变更的前置核对项是
`(tenant_id, created_at)` 索引;若缺,补一个迁移(ADR-004/006 约定,
同一 change 内一次建全,不留追补)。若后续窗口 count 成为热点,再议
增量计数器,本变更不预建。

## D5 为什么不动 agent 面并发上限

限流回答的是"允不允许这次请求进去",并发上限回答的是"同时放多少进去"。
后者是容量治理(需要信号量 + 队列 + 超时策略),与 LLM 供应商侧的并发
配额(EKS/QPS)相关,收益与风险都远大于本变更。两者叠加做会让一个变更
同时改控制面与 agent 面,违反"一个 change 一个能力域"。故明确划到界外。

## D6 前端契约面的最小改动

新增两个 detail 码即可,不引入新的响应结构:前端
`ERROR_CODE_LABELS` 已有 21 条同形态映射,补两条零成本。错误文案必须
落在既有「错误文案转译单源」里,不允许在页面里另写分支——
那是重复造第二轮子。
