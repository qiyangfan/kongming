# Design: add-voice-call-guards

## Context

动机与范围见 proposal.md。本设计直接相关的事实分两类:上游服务边界与当前代码形态。

### 生态对照(2026-11-25)

| -------------------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------- |
| OpenAI Realtime / GPT-Live                                           | Realtime:浏览器/移动端推荐 WebRTC,WS 用于服务端;GPT-Live 连服务端到服务端也优先 WebRTC | WebSocket 或 WebRTC DataChannel              | 浏览器直连音频用 WebRTC 是官方首选,WS 是服务端方案             |
| Google Gemini Live                                                  | 官方协议是 WSS;浏览器用 ephemeral token 直连,没有原生 WebRTC 直连 | WebSocket                                    | 接 Gemini 不能复用 SDP 牵线;要么浏览器 WS + 短期 token,要么服务端桥接 |
| 阿里 Qwen-Omni-Realtime                                              | WebRTC 用于浏览器实时音视频;WebSocket 用于服务端集成与原型验证   | DataChannel / WebSocket                      | 与 OpenAI 同构;WS 的定位不是浏览器低时延音频                    |

| Pipecat                                                              | WebSocket 与 WebRTC 都支持,按部署选择                            | 同一传输或独立控制面                         | 没有全局赢家,取决于谁持有媒体                                   |
| Microsoft voice-agent 示例                                           | WS 默认走「浏览器 → 本地后端 → Azure」;WebRTC 走「浏览器 → Azure」 | 后端代换/中继信令                            | WS 默认是为了中继与录音;直连方案仍是 WebRTC                    |
| HuggingFace speech-to-speech demo                                    | 默认 WebSocket(本地演示、可回放录音);WebRTC 可选                 | 同一传输                                     | WS 默认是演示取舍;WebRTC 有 NAT/录音限制                        |
| FoxESS ai-chatbot(ADR-013 引用的参考实现)                            | 浏览器持 WebRTC;后端用 Key 代换 SDP,不返回 Key                   | 工具/业务调用走 HTTP                         | 凭证与媒体分层同本仓;它只有每分钟建连率与本地会话时长,没有日预算 |

结论:WS 与 WebRTC 不是二选一,主流实现按层分工——**浏览器音频用 WebRTC,
服务端/信令/控制用 WebSocket**。「大厂推荐 WS」通常指服务端集成、电话链路或
需要服务端持有媒体的场景;浏览器直连实时语音的官方推荐仍是 WebRTC。本仓的
「WebRTC 音频 + WS 文字控制」与 OpenAI server-side controls、LiveKit 同构。

传输能力因厂商而异,不能当成可移植资产:OpenAI 与阿里支持浏览器原生 WebRTC;
Gemini Live 的官方协议是 WSS(浏览器用 ephemeral token),原生 WebRTC 直连
仍是社区诉求。若未来要接 Gemini,不能复用现在的 SDP 牵线端口,只能二选一:
浏览器 WS + 短期 token(无媒体中转,但浏览器要自己做 PCM 采集/播放/回声处理),
或服务端 WebRTC 桥(LiveKit/Pipecat 一类,需要新增媒体进程)。这属于另立
provider adapter 的决策,不在本变更。

### 供应商接入闸(避免重蹈 Gemini 的覆辙)

当前唯一登记的 profile 是「阿里 WebRTC 直连 + 服务端 SDP 代换」。新增语音供应商
前,必须先把下面四项写清楚;只改 `voice_realtime_base_url` / `voice_model`
不算接入:

| 维度       | 必须明确的内容                                                   |
| ---------- | ---------------------------------------------------------------- |
| 浏览器传输 | WebRTC 直连、浏览器 WS,还是服务端媒体桥                          |
| 凭证模式   | 服务端代换 SDP、ephemeral token,还是媒体桥专用凭证                |
| 事件协议   | DataChannel 还是 WebSocket,事件 schema 与本仓状态机的映射关系     |
| 会话配置   | VAD/断句、工具调用、音色与音频格式是否与现有配置同构              |

边界要保持:状态机、文字控制通道、语音轮绑定、审计、准入与预算都是传输无关的;
换供应商只应替换 provider adapter 与浏览器媒体层,不应重写这些。WS-only 供应商
(Gemini)不能只改配置接入,也不能把「浏览器 WS + 长期 Key」当作捷径。

### 媒体中转的容量口径

「音频不经过后端」是容量与时延上的优化,不是硬限制。是否中转按下面的量级判断,
不要按感觉判断:

| 路径                             | 每路带宽(双向)            | 当前 2 路并发 | 100 路并发 |
| -------------------------------- | ------------------------- | ------------- | ---------- |
| 直接 WebRTC(当前)               | 0(媒体不过服务器)         | 0             | 0          |
| 中转 Opus                        | 约 0.07–0.1 Mbps          | < 0.2 Mbps    | 7–10 Mbps  |
| 中转裸 PCM(16k 入 + 24k 出)     | 约 0.64 Mbps(WS 约 0.85)  | 1.3–1.7 Mbps  | 64–85 Mbps |

结论:

- 当前 `KM_VOICE_MAX_CONCURRENT=2` 下,即使按最贵的裸 PCM 中转,带宽也只有
  兆级,打不爆网卡;真正的瓶颈是 CPU(转码、抖动缓冲、加密)与进程模型。
- 不要把媒体搬进 FastAPI 进程。若重开中转,用独立媒体服务(LiveKit/Pipecat/
  Pion 一类)、浏览器侧用 Opus、服务端只做必要的 Opus↔PCM 转码,并按实测
  并发定 `KM_VOICE_MAX_CONCURRENT`;TURN 也要独立部署与计量。
- 接 Gemini 这类 WS-only 供应商时,服务端↔供应商通常是 PCM + base64(约
  0.85 Mbps/路),浏览器↔服务端用 Opus;这一条比「浏览器直连」多一个转码
  环节,容量评估要按独立媒体服务做。

**决策(2026-11-25):本阶段不引入中转。** 现在没有「WS-only 供应商」「受限
网络」「服务端录音/电话」或「多供应商故障切换」的承诺需求;中转不会自动带来
厂商可移植性,还会增加媒体服务、TURN、转码、CPU、安全面与运维,并劣化时延。
带宽不是决策因素(2 路 < 2 Mbps,100 路 Opus 约 7–10 Mbps),不值得为它付
复杂度。

重开条件(任一成立才立项,不在本变更):① Gemini 等 WS-only 供应商成为承诺
需求,且浏览器 WS + ephemeral token 的体验不可接受;② 受限网络、SIP/电话或
服务端录音成为承诺需求;③ 并发超过直连可承受范围或供应商限制成为瓶颈;
④ 多供应商故障切换成为产品需求。触发后优先托管或成熟开源媒体服务,不自研
Python 媒体泵;先做 10/50/100 路压测再定并发上限。

参考实现还印证了两件事:后端代换 SDP、不返回 Key 是同类产品的共同做法;它的
`sessionSeconds` 也明确写着「本地语音会话授权时长,不代表供应商强制断连」,与
本变更识别的收口边界一致。差别在于它只有每分钟建连率与单会话 TTL,没有
24 小时建联预算;本变更补的是这一层。

结论:上游对「僵尸会话」只有 120 分钟硬上限,没有并发会话总数限制,也没有服务端
关闭接口。把暴露面压到可接受范围只能靠部署侧预算。

### 当前代码形态

- 收口:`VoiceService.end_call` 释放准入并落审计;`_close_out` 向浏览器发
  `call.end` 并关闭文字通道(`apps/api/kongming/voice/service.py`、
  `apps/api/kongming/voice/router.py`)。没有任何向模型服务关闭会话的调用。
- 媒体:浏览器与模型服务 WebRTC 直连,后端只看到 SDP 文本;后端无法关闭 DTLS/SRTP。
- 准入:Redis 同用户单通 + 并发槽;票据 60 秒、`GETDEL` 一次性;均与通话表同进程。
- 审计租户:建交通话直接把 `X-Tenant-Id` 原值写进通话快照
  (`apps/api/kongming/voice/router.py`),没有走
  `kongming.tenant.resolve_tenant`。
- 票据传输:`openVoiceChannel` 把票据拼进 URL query
  (`apps/web/src/lib/api.ts`);已在本机 uvicorn
  `websockets_impl.py` 确认访问日志使用 `get_path_with_query_string(scope)`,
  query 会落日志。
- 限流设施:`RedisRateLimiter`(固定/滑动窗口)与成本闸已存在,但 voice 域
  没有接入;准入自己的 Lua 脚本在 voice/repository。

## Goals / Non-Goals

**Goals:**

- 让「恶意客户端保留会话」的最坏成本由服务端预算封顶,不依赖浏览器配合。
- 修补审计归属、票据日志暴露与超大帧三个小口子。
- 把上面的取舍与上游硬边界写成 ADR,不再使用「准入封顶暴露面」这种只对诚实
  客户端成立的表述。

**Non-Goals:**

- 不改变媒体直连、不让后端代理音频、不下发临时 API Key。
- 不做强制收口(心跳/证明/人机校验)。
- 不做精确计费或账单对账;预算按成功建联次数近似。

## Decisions

### D1 接受收口边界,用服务端预算闸补偿

| 方案                                    | 评价                                                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 媒体改回后端转发 / 部署 SFU             | 违背 ADR-013;每路约 0.85 Mbps 与多一跳时延;只为恶意客户端付常态成本,否决                              |
| 下发临时 API Key 让浏览器直连          | 权限继承父 Key 全部能力、TTL 最长 30 分钟、不能提前删除;暴露面比服务端牵线更大,否决                    |
| 心跳/人机校验/客户端证明                | 恶意客户端可伪造,只增加正常路径复杂度,否决                                                            |
| **服务端频次 + 24 小时建联预算(选)**   | 预算计数发生在后端,客户端无法伪造「没建过联」;上游 120 分钟硬上限决定单次最坏暴露,两者相乘即成本上限 |

WS 的优势是穿受限网络、服务端持有媒体、便于录音与电话链路;但用在浏览器音频上,
要么把长期 Key/临时 Key 下发浏览器,要么把音频经后端中继。前者与「密钥不出 api」
冲突,后者与「音频不经过后端」冲突。若未来把「受限网络可用」或「服务端录音」
列为真需求,重开媒体中转/TURN 议题,而不是把当前浏览器音频改成直连 WS。

预算按**成功建立的通话**计数:每次成功牵线都可能产生一个最长 120 分钟的模型会话,
只释放准入不释放预算。建立失败(上游拒绝、票据签发失败)释放已占额度,避免上游
故障吃掉用户预算。

### D2 计数维度、窗口与原子性

- 维度:用户(发起人)+ 部署(全局)。不做租户/IP 维度:当前无真实租户,共享
  出口还会误伤;多租户配额另行立项。
- 频次窗口:固定 60 秒,key `voice:guard:rate:<user>`;超限不递减(窗口内持续拒绝)。
- 预算窗口:滚动 24 小时,key `voice:guard:user:<user>` 与 `voice:guard:deploy`;
  首次占用时 `EXPIRE 86400`。不使用自然日:无需在领域层引时区与跨零点边界,
  语义也更容易解释为「最近 24 小时」。
- 原子占用:`INCR` → 若为 1 设 TTL → 超过上限则 `DECR` 并返回失败;释放:
  `GET` 大于 0 才 `DECR`。用户与部署两次占用按顺序执行,部署失败时回滚用户。
  计数在 Redis,多实例共享;进程异常退出最多损失一个窗口额度。
- 计数时机:频次 → 用户预算 → 部署预算 → 准入 → 牵线 → 票据。任何后续失败
  逆序释放预算;成功则保留。准入的用户单通保证同一用户没有并发建联,避免
  check-then-act 竞态。
- 默认值:频次 6/分钟、用户 20 通/24 小时、部署 100 通/24 小时;全部可配置,
  0=关闭。频次 6 给重拨留余量,同时低于上游 RPM 60;用户 20 与部署 100 对演示
  规模足够。金额不能按固定「元/分钟」线性推算(见下文成本口径),所以用次数上限
  加账单告警兜底。

### D3 故障语义

- 准入继续 fail-closed(读不到 Redis 即拒绝建立),它是保护服务器的闸。
- 频次与预算 Redis 异常时 fail-open 并告警:同一 Redis 故障会先让准入拒绝,
  不会因预算 fail-open 产生暴露;反之预算读数故障不应阻断所有诚实通话。
- 审计写失败不影响闸语义(沿用 `OperLogSink` 尽力而为)。

### D4 错误码与前端文案

| 场景           | 状态 | detail               | 前端文案                           |
| -------------- | ---- | -------------------- | ---------------------------------- |
| 单位时间太频繁 | 429  | `VOICE_RATE_LIMITED` | 操作太频繁,请稍后再试              |
| 用户预算用尽   | 429  | `VOICE_DAILY_LIMIT`  | 近期通话次数已达上限,请稍后再试    |
| 部署预算用尽   | 429  | `VOICE_BUSY`         | 当前通话人数已满,请稍后再试        |

部署预算复用 `VOICE_BUSY`(原本用于并发满,409),前端按 detail 字符串分类,
状态码不同不影响。用户预算与部署预算必须分开文案:把全局额度说成「你的额度」
会误导。

### D5 票据改子协议

- 前端:`new WebSocket(url, [ticket])`;`channelUrl` 不再拼 query。
- 后端:优先读 `Sec-WebSocket-Protocol`(逗号分隔时取第一个非空值),用该值
  鉴权,并在 `websocket.accept(subprotocol=...)` 中回选;无该头时回退 query,
  兼容一版,待前端铺开后删除回退。
- 为什么不放首个消息:要先接受未鉴权连接,多一个状态阶段,还会让未鉴权连接
  占用握手资源。
- 为什么不放 cookie:登录只认 `Authorization` 头,cookie 里是刷新令牌与 OAuth
  state,拿来当通道凭据会扩大暴露面。
- 访问日志:uvicorn `websockets_impl` 的 accept/close 日志记录
  `get_path_with_query_string`,改子协议后路径不含票据。
- 票据本身仍是一次性、60 秒、绑定本人;复用/缺失/他人票据的既有拒绝语义不变。

### D6 租户归属

- 建交通话走 `kongming.tenant.resolve_tenant`:显式 key 查绑定 + ACTIVE;
  缺省取默认租户(default 优先、最早授予、t.id tiebreak);无法确定返回
  `403 TENANT_FORBIDDEN`,与 chat/trigger 同口径。
- 解析放在读完并校验 Offer 之后,用独立短会话(与审计出口同范式),不把请求
  作用域会话带过最长 15 秒的上游牵线;慢上传也不会占着连接池。
- 审计记录校验后的 `tenant_key`;仍不进入问答链路(问答的租户由浏览器带的
  `X-Tenant-Id` 在 chat 域再校验)。
- 代价:establish 多一次索引查询,且 DB 不可用时语音建立失败。这与 chat 的
  可用性一致,可接受。

### D7 审计口径与滥用观测

- `rounds`/`interrupts`/`audio_tokens_*` 由浏览器转发的模型事件累加,只能当
  参考值;审计与文档明确「不作计费依据」。不改字段名,避免契约与既有审计消费
  方漂移。
- 日预算拒绝落 `chat.voice.call_rejected` 审计(detail 含维度、已用、上限);
  频次拒绝只记日志,避免刷审计。
- 百炼控制台的费用/用量告警由部署方配置,写进 HANDOFF;代码不新建告警系统。

### D8 WebSocket 帧上限

- api 镜像 uvicorn 加 `--ws-max-size 262144`(256KB),作为内存层硬闸。
- 应用层在 `receive_text` 后按 UTF-8 字节数检查 64KB,超限 `close(1009)` 并走
  正常收口。正常最大事件是 `session.updated` 回显(工具与指令,几 KB),64KB
  有充足余量。
- 不做事件频率闸:恶意客户端刷事件只消耗自己这一通的 CPU,且会先触发时长上限。

### D9 决策记录与文档

- 事实修正已在提案阶段落:ADR-013 加日期化补注,修正「准入封顶暴露面」只对
  诚实客户端成立的表述;`docs/tech-stack.md` 把「长驻 WebSocket 会话」更正为
  「WebRTC 媒体 + WS 文字控制」并注明本地时长不强制供应商断连;
  `docs/HANDOFF.md` 补 120 分钟硬上限、审计口径与告警建议,并更正票据/准入
  的存储位置。
- apply 时新增 ADR-014,记录上游事实、预算闸与不选方案,并把 ADR-013 的补注
  指向 ADR-014;新配置与 `.env.example` 变量随实现补。

## 成本口径

北京地域标价(2026-11-25):输入音频 ¥6/百万 Token、输出音频 ¥12/百万 Token;
`qwen3.8-omni-flash-realtime` 的音频 Token 换算为输入 `秒 × 7`、输出 `秒 × 12.5`。
只按新增音频线性估算,双向连续说 60 秒约 ¥0.0115;但每次响应会把上下文窗口内的
历史音频一并计入输入(最多 100 轮 / 600 秒,全部输入上限 196,608 Token),
长通话成本随轮次超线性增长,不能用一个固定「元/分钟」当预算依据。

因此本变更不承诺具体金额上限,只承诺次数上限:单用户 20 通、部署 100 通/24 小时。
实际金额由百炼控制台账单与费用告警兜底;北京地域有 100 万 Token 免费额度(90 天)。
要收紧成本,先调低次数上限,再考虑缩短单次时长上限。

## Risks / Trade-offs

- [正常用户触顶] → 缺省值远高于演示用量;全部可配 0 或调大;审计里能看到拒绝
  事件,便于校准。
- [滚动 24 小时与「每日」直觉不一致] → 文案用「近期」,文档写明窗口语义。
- [Redis 故障时预算 fail-open] → 准入 fail-closed 先行拒绝;两者同源,不会
  出现「准入可用但预算读不到」的常态。
- [establish 新增 DB 依赖] → DB 不可用时语音建立失败,与 chat 一致;多一次
  索引查询可忽略。
- [query 回退保留一版] → 老客户端票据仍可能进日志;只影响过渡期,前端铺开后
  删除回退。恶意客户端用 query 只暴露自己的票据。
- [上游文档数字会变] → 实现前重新核对 120 分钟/RPM/TPM;默认值不写成硬编码
  结论,预算维度不依赖具体单价。
- [多账号轮换] → 本变更不解决;注册/账号准入是另一条防线。

## Migration Plan

1. 先部署 api:新配置有缺省值;票据同时接受子协议与 query;老 web 仍可用。
2. 再部署 web:通道改子协议,新增 429 文案。
3. 回滚:三个预算/频次配置配 0 即关闭;无 schema、无数据变更;票据回退路径在,
   回滚 api 也不影响已更新的 web?反向不成立,故上线顺序固定 api → web。
4. 观察:看 `chat.voice.call_rejected` 与 429 日志,按真实用量调默认值。
