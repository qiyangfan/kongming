# 086 设计：授权标志的口径统一

## D1 把 `status` 补进功能权限侧，而不是从数据范围侧摘掉

同一事实有两个读法时先问「哪个读法已被立约」。`datascope` 主规格明文写着
「取该用户全部**启用**角色所配置的自定义部门集合的并集…不含未启用角色的配置」——
「非启用角色不授予数据范围」已是规格事实；功能权限侧不看它是**漏了一处**，不是两处可选。
反方向（摘掉数据范围侧的闸）会让「启用/停用」彻底失去意义，而 DDL 的
`CHECK (status IN ('ACTIVE','DISABLED'))` 与既有规格条文都会变成假话。故只补不加。

## D2 「主体不可确定」拒绝执行，可用性降级不越权

`data_scope` 有合法的降级先例：表无过滤列时「不改写 + 审计告警」。那条先例的锚点是
**SQL 结构事实**（这一列不存在，加了就是语法错），不是**身份事实**。
「用户查不到」与「没有任何启用角色」属于后者：此时系统并不知道该给他多大范围,
而「不过滤」不是「不知道」的诚实表达——它是把未知折算成最大权限。诚实的做法只有两种:
拒绝执行,或按最窄范围（恒假）。前者已被 083 用于 CUSTOM 空集合同样场景（规格明令禁止
把「配置缺失」伪装成「查无数据」），故本批沿同一形态。
副作用可控：正常链路根本走不到——`rbac` 规格规定无角色绑定即 403,
系统调用面（`user_id` 缺省）按立约整体豁免、不进本函数。

## D3 部门启停选「都不参与行级可见性」，不选「都参与」

两个自洽方向都试想过：

- **都参与**（DEPT/CUSTOM 也剔除停用部门）：等于给一个界面上没有开关、规格里没有条目、
  只有一条 API 字段能写的标志,赋予「一键隐去整棵子树历史数据」的能量。管理员停用部门后,
  其成员连自己部门的历史数据都看不到,且系统不给任何解释——静默消失是比静默放宽更难排查的故障。
- **都不参与**（只保留 CTE 结构递归）：范围只由「角色声明的 data_scope + 用户所属部门 +
  树结构」三件事决定,三者都可从界面上复算、可对账。停用的语义收敛为组织呈现(部门树徽标),
  与现状里 CUSTOM/DEPT 的本已行为一致——即**统一到既有多数**,而不是统一到那条孤例。

选后者。若将来确有「停用即冻结可见性」的治理需求,它必须作为显性需求立项
（含界面提示、审计说明、迁移影响评估）,不允许藏在数据范围的谓词里。

## D4 四处 `data_scope='ALL'` 判定就地补谓词，不抽公共件

`audit` / `feedback` / `toolcall` / `quality` 各有一份 `bool_or(r.data_scope='ALL')`，
历史上就以「与 014 同口径」的注释互指而非共享实现（模块依赖受 `lint-imports` 约束）。
抽一个跨模块的 `scope_service` 属结构重构：要为它新立模块依赖边、动三个模块的公开面,
而收益只是消掉三行 SQL 重复。本批的真实风险是**口径分叉**而非重复,
故用「就地补谓词 + 注释互指 + 一条横跨四处的用例」把口径钉住——
`tests/test_role_status_gate.py` 同一份数据同时喂四处，任何一处漏闸即红。

## D5 系统调用豁免与本批无交集

`internal/service.py` 在 `user_id is None` 时整体跳过 data_scope 段与绑定复校,
这是 `sql-execution` 明文立约的形态（Scenario「系统调用豁免」）。本批不收紧它：
豁免的主体是持内部令牌的受信进程,与「用户可见范围解析」不同轴。改动只作用于
带 `user_id` 的路径,因此行为变化面严格限定在「有身份、但身份解析不出范围」这一格。

## D6 不顺手补角色启停界面

角色面此前无任何写 `status` 的产品路径（只有 DDL 默认值与测试旁路 SQL）,
「禁用角色」在当下是运维/未来能力而非在用功能。本批把语义定死即可,
补界面属发明需求（且要先定「禁用后已签发的令牌/在途会话」策略,那是独立一条规格）。
定死之后再加界面,才是往一个有明确含义的开关上加按钮。
