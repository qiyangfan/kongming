# 073-prompt-fingerprint 设计

## D1 为什么是「内容哈希」而不是「版本号」

版本号需要有人维护:改 prompt 的人要记得 +1,忘记就等于版本号说谎。
内容哈希不需要任何人做任何事——资产文本变一点,指纹就变;资产不动,
跨进程、跨天、跨副本的指纹逐字节一致。

这直接决定了它能防住哪类事故:版本号方案里最常见的失败是
「prompt 改了但版本号没动」,于是指纹(版本号)给出错误的可比性承诺。
哈希方案没有这个失败模式。

代价是哈希不可读(`a3f9c1d2e4b6` 不告诉你改了什么)。可读性由 git 承担:
指纹用于比对,git log 用于溯源,两者不重复。

## D2 指纹覆盖哪些资产:为什么是四个文件的全集

候选口径有三种:

- 只覆盖 `SQL_GEN_SYSTEM`:最常见的改动点,但漏掉 summarize/understand/doc
  的修订,而这些同样影响评估分。
- 按「本轮实际用到的 prompt」逐次算:精确,但一次问答用多个 prompt,
  产物里要带一个集合,基线比对变成集合关系判断,复杂且易错。
- **资产全集一个指纹(本变更)**:一次评估跑覆盖全部资产,一个指纹即可
  判定「这两次的 prompt 是不是同一版」。误报方向是保守的——某个与本轮
  无关的 prompt 变了也判不可比,这只是少一次自动比对,不会把真回归放过去。

误报的代价是「多跑一次人工确认」,漏报的代价是「红线失真」。
在质量门禁上,选误报方向。

## D3 为什么用独立内省端点,而不是塞进 `/internal/models`

`/internal/models`(api 的 `agent_client.py:316` 在用)的语义是「模型清单」,
把 prompt 指纹塞进去会把两件无关的事耦合成一个响应:以后改模型内省
要重新评估对评估链路的影响,反之亦然。

独立端点 `GET /internal/prompt-fingerprint` 的语义单一,消费方明确
(控制面 + 评估器),且受同一 `X-Internal-Token` 中间件守门——ADR-002 的
信任边界不变,不新增对外暴露面。

代价是多一个内部端点进 OpenAPI(需 `make contracts`)。可接受:
ADR-005 的漂移门禁本就要求契约与代码同步。

## D4 「不可比」标注为什么必须由代码输出,而不是写进文档

人工口径(现在的基线纪律)依赖「看数字的人知道 prompt 动过」。把不可比
判定交给代码输出后, night 自动化(065)拿到的是**结构化的事实**而不是
需要人肉的默契:指纹不同 → 输出带不可比标注 → 红线要么不判,要么按
065 的口径要求人工溯源。

若只把这条写进 README,它与现有基线纪律是同一个脆弱点:靠人记得。
本变更的增量价值恰恰在「把记得变成不需要记得」。

## D5 为什么不做缓存/增量哈希

指纹在进程启动时算一次(assets 是模块常量,不可能在运行期变),
成本是几次字符串拼接 + 一次 SHA-256,微秒级。加缓存是为一个
本身已是常量的东西加状态,纯属多余。
