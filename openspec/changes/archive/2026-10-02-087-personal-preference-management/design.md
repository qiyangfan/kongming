# 设计：复用本人偏好资源完成自管理

## 范围与证据

- `apps/web/src/pages/MemoryPage.tsx` 当前没有 `/memory/prefs` 调用。
- `memory/router.py` 丢弃显式 null；`prefs.py` 丢弃空值；`service.py` 合并后保留旧槽位。
- `repository.py` 当前读整份再写整份，不能保证并发不同字段的合并。
- 当前显式聊天记忆也调用 `apply_implicit_patch`，必须分开人工修改与自动补齐语义。

## D1：保持资源形态，明确删除语义

| 操作 | 规则 |
|---|---|
| GET `/memory/prefs` | 返回本人当前租户的合法槽位，外层仍为 `prefs` |
| PUT 省略字段 | 保留已有值 |
| PUT 合法非空值 | 覆盖对应槽位 |
| PUT 显式 null | 删除对应槽位 |
| PUT `{}`、空字符串、空列表 | 维持既有空补丁归一化；没有非空设置或 null 删除时为真正无操作 |
| DELETE `/memory/prefs` | 清空全部槽位，200 返回 `{ "prefs": {} }` |

PUT 请求继续是直接槽位对象，不新增 `prefs` 请求包装。保留未知字段、类型错误的 422。接口不接受指定他人的 user_id；Bearer 的 401、租户前置校验的 403 与既有资源越权 404 语义保持各自边界。

归一化后既没有非空设置、也没有显式 null 删除指令的 PUT 返回当前配置，不创建或修改行、不递增人工版本、不使在途自动补丁失效，也不伪造修改审计。含显式 null 的请求属于有效人工指令，即使目标槽位已不存在，仍推进人工版本。

## D2：一个内部人工版本，短事务合并

`user_prefs` 增加 `manual_revision BIGINT NOT NULL DEFAULT 0`，仅内部使用，不进入公共响应，不保存历史记录。保留现有 JSON 列，新建 Alembic 迁移。

人工页面的有效修改以及聊天中显式写槽位：确保本人本租户行存在，短事务锁行，基于最新配置合并，再递增人工版本。全部清空保留空行，已空时仍递增版本，避免旧任务因重新建行回到版本 0 而复活偏好。不同字段的并发人工修改均保留；同字段按锁内提交顺序生效。

自动提取：在源问答准备阶段、任何 LLM 调用之前捕获版本，同步与流式后台任务均携带该快照。落库时短事务检查人工版本一致，只补缺失槽位，不删除或覆盖已有槽位；版本不一致则放弃本轮补丁。自动写入不递增人工版本，不同自动补丁仍可串行合并。

不跨 LLM 持锁。版本读取失败时跳过本轮自动写入，不将未知版本当作 0；空提取不创建配置行。清空之后开始的新问答可学习新的偏好，本件不增加永久禁学策略。

## D3：在现有页面完成操作

使用现有页面、生成类型与标准组件。字符串槽位使用文本字段，metric_aliases 使用可编辑列表；清除操作发送 null，全部清空使用既有 AlertDialog，明确只影响偏好。

读取失败显示错误与重试，不用空配置掩盖失败。成功操作用响应替换本页偏好；请求缓存与表单按本人及租户分区，切租户清理表单，迟到响应不能覆盖新语境。NOTE 列表、导出和删除保持现有行为。

审计记录本人、租户、操作类型及受影响槽位名，不额外记录偏好原文或历史快照。
