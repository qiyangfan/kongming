# Proposal: 通用工具网关(外部工具域接入框架)

## Why

Kongming 通用智能体化的横向地基。当前接入外部能力的模式是「一域一特判」:SQL 域有防火墙 + 六层纵深,知识库检索(081)单独走了控制面出站,未来每接一个新工具域(web 检索、HTTP 连接器、办公文档、消息通道)都要重造一遍出站治理。把「SQL 防火墙」的治理模式**推广为声明式的工具域接入框架**(域清单 + 域策略器 + 统一出站通道),新域接入从「写一套治理代码」降为「声明一份域清单 + 实现一个策略器」,且信任边界(ADR-002)零改动。

## What Changes

- 新增工具域(tool domain)抽象:一个域 = 一组出站能力 + 一份声明式域清单(端点、出口白名单、超时、重试分类、脱敏策略、限流配额、审计标签)。
- 域策略器(policy engine)契约:每个域 MUST 绑定策略器,缺策略器的域 MUST NOT 注册(fail-closed);策略器职责 = 出口主机白名单(021 语义推广)、参数校验、响应脱敏(PII)、超时与重试分类(连接层未送达重试至多一次 / 响应类错误不重试)。
- 统一出站通道:控制面单点出站(鉴权/白名单/超时/审计切面),域执行器只做协议适配;Agent 面恒经既有 `/internal/tool/execute` 回调,**不新增任何通道**。
- 域级审计与失败采集:成败均落既有 sys_tool_audit(带域标签),失败分类对齐既有 unreachable/protocol 口径,非 LLM 调用不入用量。
- 迁移验证:把 knowledge_search 收编为网关上的第一个域,external-knowledge spec 全部场景逐字段回归零漂移。
- 治理面:域清单/启停状态并入既有工具管理面口径(system:tool:manage),部署级条件注册语义与 tool-calling 对齐。

## Capabilities

### New Capabilities

- `tool-gateway`: 外部工具域的声明式接入、域策略器契约、统一出站通道、域级审计与治理——新工具域接入框架的全部行为契约。

### Modified Capabilities

(无——工具注册表/管理面既有 requirement 的行为不变;域清单为新增端点,不改既有工具清单语义。)

## Impact

- `apps/api`:新域包 `toolgateway/`(域清单装载/策略器注册表/出站通道/审计切面);`internal/` 既有工具执行回调按域分发改造(分发面,行为零回归);`knowledge_search` 执行器迁移到网关域。
- 域策略器是安全规则类:测试先行(白名单拒绝/缺策略器不注册/脱敏漏斗),宪法 Article III。
- 出站白名单推广自 021 model_allowed_hosts 语义,复用既有配置面。
- Agent 面**零改动**(设计硬约束);内部回调形态不变;勘误:治理面三端点(`/system/tools/domains` 及域启停)随本变更进入 OpenAPI 公开面(既有系统管理路由前缀),契约随 `make contracts` 再生成,web 未消费。
- 无 schema 变更(域清单为部署配置,不落库);无 web 改动(管理面展示走既有工具管理端点的纯增字段)。

## Non-goals

- 不实现任何新工具域(web 检索、HTTP 连接器、邮件/Slack 通道等)——每个域是后续独立变更,本变更只交付框架 + 一个既有域迁移验证。
- 不改造 MCP 出站(mcp-interop 域既有行为不动,是否收编网关待框架落地后单独评估)。
- 不做域的热加载(域清单变更随进程重启生效,与部署级工具注册语义一致)。
- 不引入消息队列/异步任务框架做出站编排(出站仍是同步回调语义)。
- Agent 面不做任何改动(不新增感知面)。
