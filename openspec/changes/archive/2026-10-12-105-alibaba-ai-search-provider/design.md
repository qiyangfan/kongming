# Design

## Context

- websearch 域供应商适配形态(094 定):适配注册表单源(供应商 id →
  端点主机 + 请求/响应映射函数),域清单端点与白名单由配置派生;检索卡
  整形与畸形收口在域策略器(通用,供应商无关)。
- zhipu 接入(094 收尾批)是最近一次实例化先例:两条映射 + 枚举一项 +
  桩测试,复现形态照抄。
- 阿里云 AI 搜索开放平台联网搜索 API 契约已核对(鉴权头形态/请求参数/结果列表
  结构),报文样例留作测试夹具。

## Goals / Non-Goals

**Goals:**

- 实例化成本压到最小:框架代码零改动(改到框架即本变更做错了)。

**Non-Goals:**

- 该平台的非联网搜索产品面(自建索引引擎/向量检索/排序插件等,非本域语义)——只接「通用联网搜索」
  一条产品线的 web 检索语义。
- 供应商运行时切换/多供应商并行(单供应商配置,既有语义)。
- 真实 key 的 e2e(外部条件,非本变更可完成;HANDOFF 留配方)。

## Decisions

1. **映射函数挂既有适配注册表**(与 tavily/bocha/zhipu 同构),供应商
   枚举扩展一项;白名单主机由派生机制覆盖,不新增配置面。
2. **桩测试用真实报文样例夹具**:以核对过的报文(成功/畸形/空结果三类)
   为静态夹具,映射函数纯函数直测——不 mock 网络层,不依赖 key。
3. **鉴权头装配在映射内**:该平台鉴权头形态(`OS-` 独立 key,与 zhipu 的 bearer
   不同)收在请求映射单点,出站通道只负责传输(既有分工)。

## Risks / Trade-offs

- [真实 API 与核对契约漂移(文档≠实测)] → e2e 待 key 补验是既定步骤;
  畸形报文显式失败路径保证漂移时不静默吐空。
- [映射细节遗漏(分页/条数上限语义)] → 夹具样例覆盖典型参数形态;
  首次 e2e 时核对条数行为并回填夹具。

## Migration Plan

纯增量(注册表项+映射函数+枚举值+测试);未配置该供应商的部署零感知
(条件注册);回退即 revert。
