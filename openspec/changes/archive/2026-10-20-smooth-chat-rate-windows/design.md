# 设计：平滑问答速率窗口与原子 Redis 计数

## Goals / Non-goals

**Goals**

- 修复 Redis 固定窗口计数在键过期附近可能失去 TTL 的竞态。
- 避免登录问答和公开嵌入端点在速率窗口切换时重新获得完整额度。
- 保持现有限流身份、配置、429、fail-open、配额审计和下游调用顺序。

**Non-goals**

- 工具总配额和工具域配额仍使用固定窗口。
- 本设计不限制同时在途请求数，也不对请求进行排队或延时。
- 不改变日/月用量统计或其并发预留语义。

## Decisions

### D1：固定窗口计数递增与 TTL 设置必须原子完成

保留现有固定窗口接口与 Redis 键语义，使用 Redis Lua 原子执行递增、首次 TTL 设置和结果判定。脚本检测到已存在但没有 TTL 的旧键时，为它补上当前窗口 TTL，避免历史上因过期竞态产生的无 TTL 键继续永久生效。已有有效 TTL 不续期，保持窗口长度不因后续请求而滑动。

脚本异常仍沿用现有 fail-open：记录 error 并放行。工具总配额和工具域配额继续调用固定窗口接口，不改变限流键、阈值或审计结果。

### D2：问答速率闸使用近似滑动窗口计数

`ChatCostGate` 对登录问答和公开嵌入使用单独的滑动窗口接口；固定窗口接口继续服务工具调用。窗口长度沿用 60 秒，阈值读取现有配置。

实现按 Redis 服务端时间划分当前与前一窗口，使用加权估算：`当前窗口计数 + 前一窗口计数 × 前一窗口剩余权重`。只有估算值加本次请求不超过阈值时才递增当前窗口计数。判定和递增在 Redis Lua 脚本中一次完成，避免并发请求重复消费同一额度。两个窗口计数在不再参与判定后自动过期。

这是速率保护闸的近似估算，不承担精确审计或计费。它消除固定窗口切换造成的完整额度重置，但不限制额度内的瞬时并发突发。精确调用数仍由既有 `sys_llm_usage` 计量路径负责。

### D3：保留现有策略边界

- 登录问答键继续包含租户与用户；公开嵌入键继续包含助手与可信客户端 IP。
- 超限仍返回既有 `CHAT_RATE_LIMITED`，且不调用 Agent/LLM。
- Redis 不可用仍 fail-open；日/月配额仍由现有独立闸门判定。
- 工具调用及各工具域继续使用固定窗口；不增加全局 HTTP 限流、漏桶队列或并发信号量。
- 不新增配置、依赖、表、迁移或 OpenAPI 变更。

## Risks / Trade-offs

- 滑动窗口计数是近似值，边界处可能比精确日志窗口略宽松或略严格；这符合速率闸用途，不替代精确计量。
- 两类 Redis 脚本都必须保持单次原子执行，并对键过期、Redis 异常和并发调用进行回归验证。
- 近似滑动窗口减少边界突发，但不限制同一窗口内并发进入的请求；若观测证明需约束在途 LLM 并发，应另行定义容量治理变更。
- 此变更不会为历史所有可能的异常键做全库扫描；固定窗口脚本在访问到无 TTL 旧键时会补 TTL。
