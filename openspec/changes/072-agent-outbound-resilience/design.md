# 072-agent-outbound-resilience 设计

## D1 韧性放在 agent 面,而不是控制面重试整轮问答

控制面(api)当然也可以对 `/query` 整轮重试。否掉的理由:

- 整轮重试会重烧 **3–5 次** LLM 调用,而故障往往只发生在其中一次;
  在最贵的路径上做重试,是把成本放大一个量级。
- 整轮重试无法区分「理解问题就失败了」与「总结时供应商抖了下」,
  前者重试只是重复同一失败。
- agent 面已持有全部出站客户端(LLM 与回调),恢复点天然在那里;
  控制面加一层只会多一个「谁负责重试」的歧义。

控制面唯一该做的是它已经在做的事:`agent_timeout_sec=120` 的总体时限。
本变更的尝试预算就是按这个时限反推的(见 D4)。

## D2 为什么必须区分「未送达」与「已送达」失败

这是本变更最容易被做错的一处,也是**不能无脑给所有回调加重试**的硬理由。

当前 SQL 防火墙(`packages/liannu/liannu/rules.py:22` `FORBIDDEN_FUNCS`)
对函数调用是**黑名单**而非白名单:未被列入的函数(用户自建函数、
`nextval`、`txid_current` 等)均可执行。因此「执行面 SQL 是只读的、
因而无副作用」目前**不是可证明命题**,只是一条强约束。

推论:

- 连接建立失败(请求从未送达)——重试安全,服务器侧什么都没发生。
- 读超时——请求已送达且可能已执行完;重试等于重复执行,
  在存在副作用函数的前提下不可接受。

故规则定为:`sql_execute` 仅对连接层未送达失败重试,读超时不重试。
这条规则同时写进 spec(Scenario),防止实现侧图省事按「超时可重试」一刀切。
顺带记录一项待独立立项的缺口:函数白名单化能让「只读」变成可证明命题,
届时读超时重试才具备前提;那是 sqlfw 域的演进,不在本变更。

## D3 为什么降级目标是「主模型 + 单层显式条目」,而不是 key 池或多级链

三条备选形态的现实权衡:

- **key 池**(参考项目方案):同一 provider 多 key 轮换 + 健康态。自建部署
  通常只有一个 key,多 key 主要服务于 QPS 扩容;而 agent 面禁 redis 使健康态
  只能进程内,多副本分裂后「某个 key 坏了」的判断在副本间不一致——
  这正是参考项目靠共享存储 + fail-soft 拼命修的东西。搬过来是搬一套
  修不完的机制。
- **多级降级链**:A→B→C 会让「这次答案出自哪个模型」变成追责黑箱,
  与 multi-model-routing 域「用量记录实际模型」的可审计性冲突。
- **主模型兜底 + 单层显式 fallback**(本变更):主模型由 `llm_*` 环境变量
  保证恒存在,不需要任何新配置就能接住「任务路由目标挂了」这一类
  (也是最常见的一类:把强模型配给了 SQL_GEN,强模型供应商抖动)。
  主模型自身也失败时需要跨 provider 时才显式声明 `KM_AGENT_LLM_FALLBACK_ENTRY`,
  缺省关闭——没有数据表明需要时不开。

附带收益:降级不需要新增注册表字段或表(参考项目的 `fallbackModelKey`
在 DB 模型配置里),一个环境变量即闭环。

## D4 尝试预算为什么把「降级」算进最后一次

上层 `agent_timeout_sec=120`(api 侧 httpx 超时)是硬墙。若允许
「同目标重试 2 次 + 降级目标再重试 2 次」,最坏耗时 = 2×30 + 2×30 + 退避
≈ 122s,必然穿透上限,用户侧表现为更慢的失败——比不重试更差。

故定义为:总尝试 ≤ 3(可配),第 3 次可以是降级目标且**不再重试**。
最坏 ≈ 2×30 + 1.5 + 1×30 ≈ 91.5s,稳定落在 120s 内。

退避取 0.5s → 1.0s 指数 + 全量 jitter(同刻多请求不会同频重试);
`Retry-After` 被尊重但截断到退避上限(缺省 5s)——否则供应商一句
`Retry-After: 60` 就能把请求挂到上层超时之后。

## D5 用量为什么每尝试一条,而不是合并成一条

合并非常诱人(「一次业务调用一条记录更干净」),但会同时丢掉两件事:
失败率(038 专门为此补了 `status`/`latency_ms`)和重试放大的真实成本。
按尝试落库后:

- 「成功调用数」= SUCCESS 行,统计口径不受影响;
- 062 的按次配额含失败尝试——这是 038 的既有语义,不是新偏差,
  必须在 spec 里写明,否则 062 落地后会被当成 067 引入的 bug;
- 降级发生时 `model` 字段即实际模型,「哪次调用走了哪个模型」
  天然可追,不需要额外的降级标记字段。

代价是用量表行数在供应商抖动期上升。可接受:抖动期本来就该在成本上可见。

## D6 为什么不引 tenacity

需要的能力面:一个错误分类纯函数、一个带上限的尝试循环、一个退避函数、
一个 `Retry-After` 截断。合计约 60 行纯 asyncio,无外部状态。
引库的代价是:依赖面、以及与 openai SDK / 自研 `AnthropicClient`
两套异常体系的适配胶水。仓内既有纪律(弃 structlog、弃 prometheus-client)
已两次证明「先引后不用」的代价,不为 60 行逻辑加依赖。

## D7 Bot 模型覆盖为什么不降级

`model_override` 是 Bot 创建者的显式选择,携带两层意图:模型能力
(这个 Bot 就该用这个模型)与计价(用量落到这个模型上)。静默切到主模型
会让 Bot 的行为和成本同时偏离创建者的预期,而用户侧无任何提示。

路线是把 override 目标当作最终目标:重试仍做(同一模型重发无害),
降级不做;失败即以 `llm_unavailable` 收口,由上层按既有 FAILED 语义呈现。
这是「显式配置优先于自动恢复」的一致口径,与 022 记忆、023 语义层等
「显式优先」的既有裁决同向。
