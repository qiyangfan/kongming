# Design: add-sql-semantic-guard

## Context

本轮真实链路冒烟（Sakila，按租赁月份统计门店笔数与支付金额）显示，单靠提示词无法形成可靠约束：

- 同一问题和相同数据源多次运行，分别出现 `payment` 行数当租赁笔数、`COUNT(r.rental_id)` 被支付一对多行放大、以及用 `inventory.store_id` 代替租赁经办员工所属门店；
- 清理历史样本、补充提示规则、播种关系后，模型仍会在 `inventory.store_id` 与 `staff.store_id` 之间漂移；
- 这些错误 SQL 都能通过语法和防火墙校验并成功执行，现有 `validate` 只做安全/语法预检，没有业务语义判定。

现状结构：

- RAG 返回 `schema_hint` 文本（表说明、列说明、关系提示、历史 SQL），Agent 把文本直接拼进提示；
- Agent 的 `validate` 只做 SQL 安全和语法预检；错误语义在 execute 后不可逆；
- 表关系与主键/外键内省已有语义层基础，但生成后没有结构化消费；
- 当前正确性主要靠提示词，缺少能单测的拒绝条件。

## Goals / Non-Goals

**Goals:**

- 让生成与校验共享同一份结构化 schema 图（表/列/主键/外键/可确定角色）。
- 对能确定性判定的错误 SQL 在执行前拒绝，并给出可执行的定向修正提示。
- 结构上可判定的业务口径错误不进入执行层；重试耗尽明确失败。
- 用公开数据和合成 gold 验证机制，不依赖真实用户样本。
- 保持旧 Agent/旧图缺失路径的最大兼容。

**Non-Goals:**

- 不改变 `query_history` 回写/召回策略，不以历史数据修复作为正确性保证。
- 不引入模型裁判作为门禁，不把语义判断外包给第二次 LLM。
- 不承诺所有业务口径都能被结构规则识别；无法确定角色时不硬拒绝。
- 不改外部问答 API、权限、防火墙、data_scope 或数据库 schema。

## Decisions

### D1 以结构化 schema 图作为单一事实源

**选择：** 控制面在 `/internal/rag/retrieve` 响应中追加纯增的 `schema_graph` 字段；包含表、列类型、主键、外键边、可确定角色与来源标记。Agent 的生成提示仍可保留文本 `schema_hint`，但生成约束和校验都以图为权威。

**备选与取舍：**

| 方案 | 评价 |
| --- | --- |
| 继续把表结构塞成更长的文本提示 | 模型仍可漂移，无法做表/列/关系级别的机械判定；失败没有可回归边界 |
| Agent 直连数据库内省 | 违反 ADR-002（Agent 零凭证）；且会让生成侧重新拥有数据访问权 |
| **控制面产出图、Agent 只消费（选）** | 守住信任边界；图可缓存、可测试；旧 Agent 收到额外字段不受影响 |

图从控制面实际可用的表说明、主键/外键内省和关系数据组装，不新增表结构。字段缺失时 Agent 回退到现有文本路径，校验只启用不需要图的规则或直接跳过语义硬规则，保持旧行为。

**实现前前置：** 现有 FK 内省接口只覆盖 default 源；动态数据源（如 sakila）必须补齐同一套 PK/FK 图采集路径，复用既有 `semantic-layer` 契约，不得用人工关系行或表名规则兜底。若动态源无法取得 PK/FK，图只标记未知，语义硬规则不启用。

### D2 外键图补入桥接表

**选择：** 召回主结果确定后，按 schema 图从“问句命中的表”出发做有界路径补入：问题需要门店/员工等维度时，若事件表本身有对应外键，优先沿事件表外键进入维表；补入表带 JOIN 路径，受独立上限约束，尾部追加，主召回不被挤掉。

**理由：** 本次失败的直接原因是 `staff` 没有进入 schema 提示，模型只能沿 `inventory.store_id` 找门店。关系扩展已有框架，但依赖预先存在的关系行；本变更要求图本身来自实际主外键元数据，避免把人工关系播种当作产品前提。

**边界：** 只沿已知外键边补入，不猜列名、不按表名匹配；无路径即零扩展；图不可用或超预算时保持主召回结果。补入预算默认沿用现有关系扩展上限，路径多于预算时按与问题实体的距离排序，同距保留事件表自带外键路径。

### D3 生成后确定性语义校验

**选择：** 在 `validate` 节点增加一个纯函数式 SQL 语义校验器，输入为 SQL、schema 图、问句和关系路径；输出结构化违规项。执行前按以下顺序检查：

1. **图范围**：SQL 引用的表/列必须来自图；未知表/列直接拒绝并提示核对清单。
2. **扇出计数**：如果聚合计数的事件表在 JOIN 中连接到可能一对多的表，要求对事件主键使用 `COUNT(DISTINCT ...)` 或先做子查询预聚合；否则拒绝。
3. **角色口径**：当表的角色可确定为“事件”或“金额”时，问“笔数/次数”不得从金额角色表计数；问事件时间不得使用金额时间列。
4. **归属路径**：问门店/员工归属时，若事件表自带员工/门店外键，SQL 的门店维度必须沿该事件外键路径；如存在事件表自身路径，却使用商品/库存等被操作对象所属门店，拒绝。
5. **其余**：无法从图确定的业务语义不参与硬拒绝；保留现有防火墙、语法、执行校验。

**角色判定：**

- 首版只用结构证据：主键/外键、事件时间列、金额数值列、唯一关系路径。
- 事件表：有自身主键、事件时间与参与实体外键；**被金额表以外键引用不否定事件角色**——事件表通常正是金额表的外键目标。
- 金额表：有金额列并以事件外键指向事件表；维表：被其他表外键引用且无事件时间/金额特征。
- 多角色、多候选路径或证据冲突 => 角色视为未知，不做 D3 第 3/4 条硬拒绝。
- 不在代码里写任何业务表名；Sakila 用例只进测试。

**备选：**

| 方案 | 评价 |
| --- | --- |
| 继续加提示词规则 | 已实测漂移；不可单测、无法 fail-closed |
| 用第二个 LLM 评审 SQL | 引入额外成本和非确定性，无法证明门禁；本变更不做 |
| **AST 规则 + 图 + 定向自愈（选）** | 可单测、可拒绝、成本低；只覆盖结构可判定的错误，边界明确 |

### D4 违规进入定向自愈，耗尽 fail-closed

**选择：** 校验器返回违规类别、涉及的表达式/表/路径和一句修正指令；selfheal 把这条具体指令拼到下一轮生成提示，不把整段规则重复一遍。重试沿用既有预算；耗尽后返回“无法生成可靠 SQL”的失败终态，不执行错误 SQL，不伪造结果。

**理由：** 现有 selfheal 只按数据库错误分类；语义违规没有执行错误可借，必须在执行前产生可读信号。定向指令比泛化“请修正”更可验证，也能避免重复调用的无界重试。

### D5 观测与兼容

- stage trace 记录 `guard` 阶段与违规类别（不回传完整敏感 SQL 到用户侧）；成功 SQL 的 trace 与现有阶段保持兼容。
- 旧 Agent 不读取 `schema_graph`，照旧用 `schema_hint`；旧召回没有图时，新 Agent 跳过硬语义规则，保持现有行为。
- 用户侧 OpenAPI 不变；内部 RAG 响应是纯增字段，需同步生成类型与 `contracts/openapi.json`。

### D6 评估策略（无真实用户）

- 用现有 Sakila 公开数据和 28 道 gold，加本次“按月租赁笔数/支付金额”用例；不依赖清洗后的历史样本作为验收条件。
- 把每个违规类别做成可判定的 SQL 变体：正确 SQL、金额表计数、库存门店、未去重计数、未知表/列；对校验器做表驱动单元测试。
- Agent 层用固定假图做集成测试，验证拒绝/自愈/终态；真实模型只用于少量实验室 smoke，不与 CI 概率绑定。
- 指标：违规 SQL 拦截率、正确 SQL 误拒率、修复成功率、无执行失败率；只在实验室结果上记录，不外推生产。

## Risks / Trade-offs

- **误拒正确 SQL**：结构规则可能把合法写法判错。缓解：角色/路径不确定不硬拒绝；先以表驱动测试覆盖；把“阶段可跳过”作为回归条件。
- **图过期**：数据源结构变化后图仍是旧快照。缓解：图由召回时缓存的内省结果生成，按数据源失效；过期时校验只做图内已知项，不做猜测。
- **图补入预算挤掉主召回**：缓解：图扩展始终尾部追加，主召回优先；超预算先裁扩展。
- **语义覆盖不足**：本变更不解决所有业务口径，只解决结构上能证明的类别；剩余问题保留在评估与后续提案，不伪装成已解决。
- **内部契约变化**：新增字段需要类型生成与 contracts 产物同步；旧 Agent 兼容由“未知字段忽略”保证。

## Migration Plan

1. 先在控制面加纯增 `schema_graph` 和桥接补入，旧 Agent 无影响；生成契约产物。
2. 再在 Agent 加消费与校验；旧图缺失路径保持现状，新图可用时逐步启用硬规则。
3. 用实验室 gold 做回归；违规拦截率和正确 SQL 误拒率达标后再允许默认启用。
4. 回滚：Agent 关闭语义校验即回到现有 validate；API 保留纯增字段，旧客户端不受影响。无数据库迁移。

## Open Questions

- 图扩展上限是否复用 `rag` 关系扩展的现有上限，还是以路径长度单独配置；实现时以最小可测常量为准并在 tasks 记录。
- 事件/金额角色的结构规则是否需要暴露为语义层显式覆盖；首版先不新增存储，歧义不硬拒绝，若真实数据出现歧义再单独提案。
- 是否把 guard 违规率纳入质量看板；先复用 stage trace，不新增表。
