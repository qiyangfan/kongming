# 设计:多智能体协作编排

## 范围与证据

- 现状:custom-agent(025)Bot = 独立问答入口,无运行时组合;workflow-orchestration(024)= 人编排静态 DAG,节点非自主智能体;tool-calling ReAct 内核 = 单实例自主循环。缺的是「运行时由 planner 动态分派给多智能体」的一层。
- 090 任务内核提供宿主(步骤/预算/审批/事件),本变更是它的一种执行策略——不另起炉灶。

## D1:orchestrator 是循环不是图

协作编排器 = agent 面一个「规划-派发-聚合-裁决」循环:LLM 拆解子任务 → 派发 worker(每次派发 = 一次既有 ReAct 内核调用,bot_system_prompt 注入人格)→ 收结构化结果 → 聚合(必要时再派发/critic 审查)→ 回写步骤结论。否决「编译成 DAG 交给 workflow 引擎」:动态性(聚合结果决定后续派发)是本变更的存在理由,静态图引擎表达不了;否决「常驻 agent 进程池」:worker 是无状态调用(上下文在派发时给定),复用既有内核进程即可,不新增部署单元(宪法 I)。

## D2:worker = 一次受限的 ReAct 调用

worker 执行 = 既有 ReAct 端点调用,注入三样受限物:子目标(user 消息形态)、上下文摘要(系统提示附加段)、可选 Bot 定义。授权恒为任务归属主体——协作不引入新主体,权限面零扩大(六层防御照常)。worker 间无通道:并发 worker 输入在派发时冻结,串行后续 worker 的输入由 orchestrator 从已聚合结论中摘要生成——「通信经 orchestrator」是结构保证,不是约定。

## D3:存储与契约

两表(ADR-004/VI):`sys_agent_collab_run`(id,task_step_id,拓扑 jsonb,状态,裁决摘要,created)+ `sys_agent_collab_worker`(id,run_id,worker 序号,子目标,绑定 Bot 标识可空,状态,结论摘要 jsonb,证据引用 jsonb,trace_id,用量摘要)。端点:协作运行查询(任务维度,挂 task:* 权限体系)+ 步骤声明协作拓扑的配置面;`make contracts` 重生成。审计走既有工具审计(逐 worker 工具调用)+ 任务事件流(协作生命周期事件),不建新审计表。

## D4:失控防护的实现位置

三重上限都在 orchestrator 循环内判定,控制面兜底:(1) 深度——派发请求携带协作层级,超过配置(缺省 1)直接拒绝;(2) 并发——控制面按 (task, step) 维度的在途 worker 计数限流(与既有工具限流同机制);(3) 预算——worker 派发前检查步骤剩余预算,不足不派发;用量上报按 worker 归集。触顶/预算尽 → 步骤部分完成语义(090 诚实收口),不新建终止语义。

## D5:测试策略(安全与失控防护先行)

失败测试先行清单:无游离协作入口、worker 授权不提权(未授权工具在协作内照拒)、并发/深度上限触顶、预算继承不放大、worker 间无直连(结构断言:worker 输入仅来自派发载荷)、分歧不静默调和。聚合裁决质量类(分歧标注/critic 修订)用固定剧本用例(可重放的 mock worker 结果)而非真实多 LLM 调用。

## 风险与缓解

- token 放大:并发上限缺省保守(如 3)+ 预算硬继承 + worker 上下文摘要体积上限;用量按 worker 归集使成本可见。
- 聚合裁决漂移(LLM 偏听):结构化结果强制证据引用;分歧场景剧本化回归;critic 独立 trace 供事后审计。
- 嵌套协作失控:缺省深度 1(即不允许嵌套),放开需部署显式配置——刻意把「多智能体套多智能体」留成 opt-in。
