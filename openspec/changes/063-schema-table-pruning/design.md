# 063-schema-table-pruning 设计

## D1 为什么用术语/关键词打分,而不是 embedding 检索

三条路线摆在桌上:

1. **embedding 向量检索表名/列名/描述**:要额外一次模型调用,要建表结构
   向量索引,要处理索引失效(schema 变更、新增列)。对于一个内部 NL2SQL
   产品,这是重基建换小收益。
2. **LLM 先选表再生成(两段式)**:多一次 LLM 调用与一次往返,且把"选表"
   这个确定性较强的问题交给了概率模型——出错时无法归因。
3. **术语/关键词加权打分(本变更)**:输入全是租户已有的结构化资产——
   skillpack 的 glossary(term/aliases/definition/hint,上限 50)、fewshot
   (上限 10)、语义层指标名与业务词。零新增依赖、零新增调用、确定性可测,
   且**打分依据可解释**(命中哪条术语 → 该表入选),这直接决定了可观测性
   能做到什么程度。

选 3。它不是最优检索器,是当前信息增量/成本比最高的一步,并且它是
**纯函数**,符合宪法 Article II 可脱离容器高频测试的要求。

## D2 打分输入与权重(初值,apply 阶段用 eval 调)

- 问题命中表名 / 列名(精确串):权重最高——这是最强信号。
- 问题命中 glossary term 或 alias:高;命中 fewshot 的 question 文本:中。
- 命中语义层指标名或其 business_terms:高(指标口径直接指向表)。
- 命中表说明文本中的业务词:低(说明常是泛描述,噪声大)。

权重设为可调常量而非配置项:过早开放成配置会产生"没人知道该调哪个"
的维护面。eval 数据说话后再决定是否提升为配置。

## D3 为什么缺省 N=12,以及为什么 zero-hit 必须不劣化

N 的两端:太小(如 3)会漏表,产生假 `NO_RELEVANT_TABLE`——这是**用户可见的
质量倒退**;太大(如 30)省不下 token 也收不敛注意力。取 12 是在"常见单
域问题涉及 3~8 张表 + 容错"之间的保守值,并保留配置项供大 schema 租户上调。

zero-hit(问题与任何表零命中)时必须维持现有哨兵行为而不是硬凑 top-N:
硬凑等于把判别职责从"模型如实说没有"推给"打分器随便选几个",这是质量
倒退。故 spec 明确"预筛为空即维持哨兵路径"。

## D4 为什么留开关而不是默认永久开启

`KM_AGENT_SCHEMA_PRUNE` 缺省开,但关闭时必须能退回全量。理由:

- 对拍期需要 A/B(预筛 vs 全量)跑同一评估集,证明 Recall@K 与
  Execution Match 不退化;
- 出现"裁掉了必需表"的线上问题时,关开关即回退,不需要回滚代码。

这是 053 影子灰度教训的同构应用:可回退比"一次做对"更现实。

## D5 可观测性是这个变更的验收核心,不是附属品

表预筛一旦出错,症状是"莫名其妙说没数据"——没有归因手段就是不可维护的。
故入选依据(命中的术语/指标/列名)与被裁表数必须随 trace 下发,且
SHALL 能在用量/trace 时间线里看到。没有这一条,本变更不满足验收。

## D6 与 ReAct 观察截断的关系(澄清,非本变更范围)

有人会问"上下文爆炸不是该用子 agent 吗"。已核实:ReAct 的
`tool_dispatch` 已有观察截断(`MAX_OBSERVE_ROWS = 20`,全量结果留终态),
即**工具输出长度问题已被现有机制解决**。本变更解决的是另一件事:
入口处注入的 schema 体量。两者不重叠,也都不构成引入多 agent 的理由。
