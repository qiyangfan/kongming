# 076-metric-provenance 设计

## D1 为什么是「指标口径」这一类依据,而不是把四类依据一起做

retrieve 节点手上有四类非文档依据,逐条按「答案里是否已经可见」判定:

| 依据 | 答案里可见性 | 判定 |
|---|---|---|
| 指标口径(`metric_hints`) | **完全不可见**——SQL 只写 `SUM(a)/SUM(b)`,不写"这是毛利率、定义如此" | ✅ 必须做 |
| 表关系(`relations_hint`) | JOIN 条件在 SQL 里逐字可见 | ❌ 信息重复 |
| 历史成功 SQL(`history_sql`) | 生成技巧,非答案依据 | ❌ 展示即误导 |
| skill-pack 术语(`skill_terms`) | 别名→列的映射不可见,但需 skillpack 域改造 | ⏸ 写死重估条件 |

判定标准只有一条:**做了之后用户能否获得答案里原本不存在的决策信息**。
关系与历史 SQL 过不了这条;术语能过但要动另一个域,留条件不拍脑袋。

## D2 单一来源:字符串由结构化命中派生,而不是两处各算一遍

这是本变更最重要的设计约束,也是它几乎零成本的根源。

`SemanticService.enrich` 的现行形态已经是正确的一半:`match_metrics`
产出结构化命中,`format_metric_hints` 把它格式化成提示词文字。坏只坏在
**命中列表没有流出函数**。因此:

- 结构化命中是唯一事实源,`metric_hints` 文字段由它派生;
- 透出到终态与前端的内容与注入 prompt 的内容**同源同批**,不可能出现
  "提示词用了 A、面板显示 B"的口径漂移;
- 若反过来做(前端或终态侧按 `metric_name` 反查一遍库),就立刻产生第二事实源
  与时序差(生成后指标被改名/停用,反查结果与当轮提示不一致)——那是参考项目
  "双写口径易漂移"的同类坏味道,明确不做。

实现上的自然结果是:`enrich` 的返回类型从 `tuple[str, str]` 变为携带命中
的结构,调用方取文字段的行为不变(零回归),新消费方取命中列表。

## D3 为什么进终态,不做过程事件

与并行提案 `068-doc-answer-citations` 的同款裁决,理由也一致:口径依据面板是
终态渲染物,流式期间没有可展示的中间形态(指标命中在 retrieve 就定了,但那时
答案还没生成,提前展示会让用户以为"已经按这个口径算完了")。

新增 SSE 事件类型意味着新事件要过一遍"恰好一个终态事件"的时序不变式、
旧前端兼容、契约与测试;而收益只是把面板出现时间提前几秒。不做。

## D4 老消息为什么按空回显、明确不重算

`conversation-artifacts` 的老消息处理是确定性重算(要素都在档里)。口径命中
不适用:同一条 SQL、同一个 summary,重跑一次的指标命中可能不同(指标可被编辑、
停用、改名)。把重算值冒充当轮口径,比显示"该轮无口径记录"更糟——那是伪造依据。

因此 spec 写成 Scenario 明令不重算,防止实现侧出于"与 artifacts 对称"的直觉
补一个反查分支。这与并行提案 `068-doc-answer-citations` 对文档来源的处置
是同一原则,两处 spec 不冲突。

## D5 面板形态:指标卡而非正文内联角标

内联角标要求正文里出现 `【毛利率】` 之类的标记,即要求 LLM 在答案中标注口径——
那会把本变更从"可见性"扩成"prompt 纪律改造 + 标注清洗",直接撞上并行提案
068 正在做的引用标注与净化域,属于抢同一个工作面。

折叠指标卡挂在答案卡下方,终态一次成型,无时序错配,形态复用既有
`collapsible` 标准件,不新建骨架件;窄屏沿用卡片内纵向堆叠(375 档可读),
亮暗两态取 token 色。

## D6 为什么不展示「命中词」

`match_metrics` 的命中可能来自 `metric_name` 或任一 `business_term`。
展示命中词(用户原话被哪个别名触发)对用户没有决策价值,却会把提示词匹配的
实现细节暴露成产品语义;将来匹配规则演进(分词/向量)时,面板文案就要跟着改。
只展示"哪条指标被命中 + 其定义",与匹配实现解耦。
